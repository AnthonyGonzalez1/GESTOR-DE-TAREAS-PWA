Las 5 estrategias de caché (2/2)

Network First y Stale-While-Revalidate — y cómo combinar las 5 estrategias en un mismo Service Worker, enrutando por el tipo de recurso.

Objetivos de aprendizaje

  • ✓Implementar Network First y Stale-While-Revalidate dentro del evento fetch.
  • ✓Comparar las 5 estrategias entre sí: prioridad, comportamiento offline, y recurso ideal para cada una.
  • ✓Combinar varias estrategias en un mismo Service Worker, enrutando por el path de la petición.
  • ✓Verificar en DevTools (pestaña Network, modo offline) qué estrategia respondió cada petición.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 20. El sw.js ya responde con cacheFirst() para todo el shell. Hoy dejamos de aplicar una sola estrategia a todo, y enrutamos varias según el tipo de recurso.

1Recap de la Sesión 20

En la Sesión 20 vimos las tres estrategias más simples: Cache Only y Network Only, que usan una sola fuente sin combinarla con la otra, y Cache First, que consulta el caché primero y usa la red como respaldo, guardando la respuesta con put(). Hoy cerramos el repertorio de cinco con las dos que faltan, y aprendemos a combinarlas todas en un mismo sw.js según el tipo de recurso — que es, en la práctica, como se ve un Service Worker real.

2Network First

Este enfoque prioriza la red para obtener la versión más reciente del recurso. Si no hay conexión, se utiliza la última versión almacenada en la caché. Es ideal para contenido dinámico, como documentos HTML o datos de una API, asegurando información actualizada en línea y acceso sin conexión cuando sea necesario [1].

sw.js (fragmento)
function networkFirst(peticion) {
  return fetch(peticion)
    .then(respuesta => {
      const clon = respuesta.clone();
      caches.open(CACHE_ACTUAL).then(cache => cache.put(peticion, clon));
      return respuesta;
    })
    .catch(() => caches.match(peticion));
}

Nótese la simetría casi exacta con Cache First, de la Sesión 20: son el mismo patrón de "intenta A, si falla usa B", con A y B invertidos. Esa simetría es intencional — ayuda a recordar cuál es cuál según qué fuente aparece primero en el nombre.

3Stale-While-Revalidate

Este enfoque combina rápida disponibilidad y actualización en segundo plano. Al recibir una solicitud, se devuelve de inmediato la versión almacenada en la caché, acelerando la carga. Luego, el service worker solicita a la red la versión más reciente y actualiza la caché para futuras solicitudes. Es ideal para recursos que deben actualizarse periódicamente, pero donde no es crítico contar siempre con la última versión, como imágenes de perfil o contenido de noticias [1].

sw.js (fragmento)
function staleWhileRevalidate(peticion) {
  return caches.open(CACHE_ACTUAL).then(cache =>
    cache.match(peticion).then(enCache => {
      const actualizacion = fetch(peticion).then(respuesta => {
        cache.put(peticion, respuesta.clone());
        return respuesta;
      });
      return enCache || actualizacion;
    })
  );
}

La línea clave es la última: enCache || actualizacion. Si había algo en caché, se devuelve inmediatamente esa versión (posiblemente desactualizada — de ahí "stale"); la petición a la red sigue en curso y actualiza el caché para la próxima vez, sin que el usuario actual tenga que esperarla.

4Caso real: combinando estrategias por ruta

Un Service Worker real casi nunca usa una sola estrategia para todo. Lo normal es enrutar según el path de la petición, y aplicar la estrategia adecuada a cada tipo de recurso del Gestor de tareas:

sw.js
self.addEventListener('fetch', event => {
  const url = new URL(event.request.url);

  if (url.pathname.startsWith('/icons/')) {
    // Íconos: rara vez cambian → Cache First
    event.respondWith(cacheFirst(event.request));
  } else if (url.pathname.startsWith('/api/')) {
    // Datos de la API: deben verse al día → Network First
    event.respondWith(networkFirst(event.request));
  } else {
    // HTML, CSS, JS del shell: rápido, y se actualiza solo → Stale-While-Revalidate
    event.respondWith(staleWhileRevalidate(event.request));
  }
});

Con esto, el Gestor de tareas usa tres estrategias distintas dentro del mismo sw.js, cada una aplicada solo donde tiene sentido: los íconos cargan instantáneos desde caché, una eventual API de tareas reflejaría cambios recientes cuando hay red, y el resto de la aplicación (HTML, CSS, JS) responde de inmediato mientras se refresca en segundo plano. El proyecto real del curso no tiene todavía una ruta /api/ — la condición queda ahí como ejemplo de cómo se vería si la tuviera.

Para verificarlo: DevTools → pestaña Network, con el filtro "Service Worker" activado, muestra de qué estrategia vino cada respuesta. Activando el modo offline (Application → Service Workers → Offline), se puede confirmar cuáles rutas siguen funcionando y cuáles no — exactamente según lo previsto por cada estrategia.

Resumen de la sesión

  • Network First intenta la red primero y usa el caché como respaldo — es la simétrica de Cache First.
  • Stale-While-Revalidate responde de inmediato desde caché mientras actualiza en segundo plano — sin hacer esperar al usuario.
  • Ya con las 5 completas: Cache Only, Network Only, Cache First, Network First y Stale-While-Revalidate cubren desde lo totalmente inmutable hasta lo siempre-fresco.
  • Un Service Worker real casi siempre combina varias estrategias, enrutando por el path de la petición — nunca una sola para toda la aplicación.
  • DevTools (Network + modo offline) permite verificar, sin adivinar, de dónde vino realmente cada respuesta.
