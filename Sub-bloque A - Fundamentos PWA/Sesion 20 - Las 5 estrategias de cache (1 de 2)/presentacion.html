Antes de empezar

¿Por qué elegir una estrategia?

No hay una estrategia universal

Un ícono que nunca cambia necesita algo distinto a la lista de tareas que el usuario edita a cada rato.

Elegir mal cuesta caro

Datos obsoletos donde se necesitaba información fresca — o depender de la red donde se podía responder al instante.

La pregunta que guía esta sesión y la siguiente: si el caché y la red tienen versiones distintas, ¿cuál gana — y qué tan grave es que gane la que no debía?

SECCIÓN 02

Cache First

Busca primero en el caché; si no está, pide a la red y guarda la respuesta.

Caché → Red

sw.js (fragmento)
function cacheFirst(peticion) {
  return caches.match(peticion).then(enCache => {
    if (enCache) return enCache;
    return fetch(peticion).then(respuesta => {
      const clon = respuesta.clone();
      caches.open(CACHE_ACTUAL).then(cache => cache.put(peticion, clon));
      return respuesta;
    });
  });
}
Por qué se clona la respuesta: el cuerpo de una Response solo se puede leer una vez — aquí se necesita tanto para la página como para el caché.

Resumen de la sesión

  • Cache Only y Network Only usan una sola fuente, sin combinar caché y red.
  • Cache First consulta el caché primero, y si falta el recurso, lo pide a la red y lo guarda con put() para la próxima vez.
  • No hay una estrategia universal: la elección depende de si el recurso es inmutable, siempre-fresco, o estático con cambios ocasionales.
  • DevTools (Network + modo offline) permite verificar, sin adivinar, de dónde vino realmente cada respuesta.
  • Network First y Stale-While-Revalidate, y cómo combinar las 5 por ruta, llegan en la Sesión 21.
