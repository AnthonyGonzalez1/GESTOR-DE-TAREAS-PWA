Las 5 estrategias de caché (1/2)

Cache Only, Network Only y Cache First: las tres estrategias más simples, implementadas dentro del evento fetch. Network First, Stale-While-Revalidate y cómo combinarlas todas llegan en la Sesión 21.

Objetivos de aprendizaje

  • ✓Explicar el problema que resuelve cada una de las 5 estrategias de caché, y por qué no hay una única estrategia correcta para toda la aplicación.
  • ✓Implementar Cache Only, Network Only y Cache First dentro del evento fetch.
  • ✓Reconocer qué tipo de recurso conviene a cada una de las tres: inmutable, dinámico, o estático versionado.
  • ✓Verificar en DevTools (pestaña Network, modo offline) el comportamiento real de cada estrategia.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 19. El sw.js ya tiene el caché versionado (gestor-tareas-v2) y activate limpia versiones viejas, pero el manejador de fetch sigue siendo el mismo match() con respaldo a la red desde la Sesión 18 — hoy le pones nombre a esa lógica, y la mejoras.

1Bienvenida y recap

En la Sesión 19 abrimos la Cache Storage API y aprendimos sus operaciones sueltas: open(), put(), match(), delete(), keys(), y versionamos el nombre del caché limpiando lo viejo en activate. Pero seguimos usando esas piezas por separado, sin una lógica clara dentro del evento fetch que decida de dónde responder. Hoy empezamos a combinarlas dentro de fetch para que el Service Worker decida, automáticamente y en cada petición, si responde desde el caché, desde la red, o desde una combinación de ambos. A esas combinaciones con nombre las llamamos estrategias de caché — hoy vemos las tres primeras; las otras dos, en la Sesión 21.

2¿Por qué elegir una estrategia?

La gestión de caché en un Service Worker requiere estrategias que combinan la interfaz Cache y el evento fetch. Estas estrategias definen cómo y cuándo almacenar o actualizar recursos, optimizando el rendimiento, la disponibilidad sin conexión y la experiencia del usuario en una PWA [1]. No existe una única estrategia correcta para toda la aplicación: un ícono SVG que nunca cambia necesita una estrategia distinta a la lista de tareas que el usuario edita a cada rato. Elegir mal la estrategia produce dos problemas típicos: mostrar datos obsoletos donde se necesitaba información fresca, o depender de la red donde se podía responder al instante desde el caché.

La pregunta que guía esta sesión y la siguiente: para este recurso, si el caché y la red tienen versiones distintas, ¿cuál gana — y qué tan grave es que gane la que no debía?

3Cache Only y Network Only: los extremos

Empezamos por las dos estrategias más simples — porque cada una usa una sola fuente, nunca ambas.

Estrategia 1

Cache Only

Esta estrategia atiende todas las solicitudes desde la caché sin consultar la red. Para funcionar, los recursos deben haberse almacenado previamente, generalmente durante la instalación del service worker. El contenido solo se actualiza si el service worker se reemplaza, por lo que es ideal para recursos inmutables, como imágenes, fuentes o bibliotecas JavaScript [1].

sw.js (fragmento)
// Cache Only: nunca toca la red
function cacheOnly(peticion) {
  return caches.match(peticion);
}
Estrategia 2

Network Only

En esta estrategia, todas las solicitudes se envían directamente a la red, asegurando que el contenido siempre esté actualizado. Sin embargo, si no hay conexión, los recursos no estarán disponibles. Es ideal para datos que cambian constantemente, como información de una API o contenido dinámico [1].

1Página pideal Service Worker
→
2SW pidedirecto a la red, nunca al caché
→
3Red respondeo falla si no hay conexión
sw.js (fragmento)
// Network Only: nunca toca el caché
function networkOnly(peticion) {
  return fetch(peticion);
}

4Cache First

Esta estrategia busca primero el recurso en la caché y, si no está disponible, lo solicita a la red. La respuesta obtenida se almacena en la caché para futuras solicitudes. Es ideal para elementos estáticos que requieren una carga rápida, pero que pueden necesitar actualizaciones ocasionales, como archivos CSS, JavaScript o imágenes versionadas con hash [1].

1Página pideal Service Worker
→
2SW consultael caché primero
→
3¿Existe?sí: responde de inmediato
→
4-5Si no:pide a la red y guarda la respuesta en caché
sw.js (fragmento)
function cacheFirst(peticion) {
  return caches.match(peticion).then(enCache => {
    if (enCache) return enCache;
    return fetch(peticion).then(respuesta => {
      const clon = respuesta.clone();
      caches.open(CACHE_ACTUAL).then(cache => cache.put(peticion, clon));
      return respuesta;
    });
  });
}

Por qué se clona la respuesta: el cuerpo de una Response solo se puede leer una vez. Como necesitamos entregarla a la página y guardarla en el caché, clone() crea una segunda copia independiente antes de que se consuma.

Para verificarlo: DevTools → pestaña Network, con el filtro "Service Worker" activado, muestra de qué estrategia vino cada respuesta. Activando el modo offline (Application → Service Workers → Offline) tras la primera carga, Cache Only y Cache First siguen respondiendo; Network Only falla — exactamente como predice cada estrategia.

Resumen de la sesión

  • Cache Only y Network Only usan una sola fuente, sin combinar caché y red.
  • Cache First consulta el caché primero, y si falta el recurso, lo pide a la red y lo guarda con put() para la próxima vez.
  • No hay una estrategia universal: la elección depende de si el recurso es inmutable, siempre-fresco, o estático con cambios ocasionales.
  • DevTools (Network + modo offline) permite verificar, sin adivinar, de dónde vino realmente cada respuesta.
  • Network First y Stale-While-Revalidate, las otras dos estrategias, y cómo combinar las 5 por ruta, llegan en la Sesión 21.
