APIs de dispositivo (1/2): cámara, micrófono y ubicación

Hasta hoy el Gestor de Tareas vivía dentro del navegador. Hoy sale al mundo físico: abre la cámara, mide el micrófono y pregunta dónde está el usuario — y, sobre todo, aprende a hacerlo sin invadirlo: permisos pedidos en contexto, errores que se explican, y una app que sigue funcionando cuando le dicen que no.

Objetivos de aprendizaje

  • ✓Explicar el modelo de permisos del navegador (contexto seguro, gesto del usuario y los tres estados granted/denied/prompt) y por qué cada API de dispositivo lo respeta.
  • ✓Abrir la cámara y el micrófono con getUserMedia, capturar una foto con <canvas>, y liberar el hardware cuando ya no se necesita.
  • ✓Obtener la ubicación con Geolocation, distinguir getCurrentPosition de watchPosition, e interpretar la precisión que devuelve.
  • ✓Diseñar los errores y la negativa del usuario como parte normal del flujo: mensajes claros y una app que sigue funcionando sin el permiso.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 23. El Gestor de Tareas con IndexedDB y nota cifrada (Sesión 22), el sw.js generado por Workbox, el indicador de conexión y el botón de instalación (Sesión 23). Hoy le agregamos un módulo nuevo, dispositivo.js, y una fila de adjuntos por tarea.

1Dónde estamos

El Gestor de Tareas ya es instalable (Sesión 16), tiene un Service Worker que lo hace funcionar sin conexión (Sesiones 17-21), guarda sus datos en IndexedDB con una nota cifrada (Sesión 22), y su sw.js lo genera Workbox (Sesión 23). Todo eso ocurre dentro del navegador. Hoy empieza el último tramo del Sub-bloque A: tres sesiones (24, 25 y 26) donde la app se conecta con el dispositivo — cámara, micrófono, ubicación, sensores de movimiento y notificaciones. Es lo que más distingue a una PWA de una página web común, y también lo que más cuidado exige, porque cada una de esas APIs toca algo personal del usuario.

2El modelo de permisos: tres condiciones antes de tocar el hardware

Todas las APIs de dispositivo siguen el mismo modelo, y entenderlo una vez te sirve para las tres sesiones de este tramo. Para que el navegador te entregue la cámara, el micrófono o la ubicación, tienen que cumplirse tres cosas:

1 · Contexto seguro

La página debe servirse por HTTPS, desde localhost, o ser un archivo file://. En una página HTTP normal, navigator.mediaDevices ni siquiera existe (vale undefined) y getUserMedia falla con TypeError. Geolocation también exige contexto seguro.

2 · Permiso del usuario

La primera vez, el navegador muestra un aviso y el usuario decide. El permiso se concede por origen, y su duración depende del navegador: puede ser de sesión, de un tiempo, o permanente.

3 · Momento adecuado

Pídelo dentro del clic en el que el usuario lo quiere, nunca al cargar la página. Un aviso de cámara sin que nadie pulsara "foto" se rechaza por reflejo — y un permiso denegado es difícil de recuperar.

Estados del permiso

Para cada permiso hay tres estados: granted (concedido), denied (bloqueado) y prompt (todavía no se ha preguntado). Se consultan con la Permissions API.

Consultar el estado sin molestar al usuario

navigator.permissions.query te dice el estado sin mostrar ningún aviso. Sirve para adaptar la interfaz antes de que el usuario pulse nada (por ejemplo, explicar cómo desbloquear la cámara si ya está en denied). No todos los navegadores soportan todos los nombres, así que se envuelve en try/catch:

dispositivo.js
export async function estadoPermiso(nombre) {
  try {
    const r = await navigator.permissions.query({ name: nombre });
    return r.state;            // "granted" | "denied" | "prompt"
  } catch {
    return "desconocido";      // el navegador no soporta ese nombre
  }
}
Medido, no supuesto. Probé estadoPermiso en Chromium con Playwright: con los permisos de cámara y ubicación concedidos devolvió granted para ambos; con un nombre inventado devolvió desconocido (el catch funcionó). Un detalle de la prueba: sin conceder nada, Chromium en modo automatizado respondió denied y no prompt — en un navegador normal, el primer encuentro con la página sí debería dar prompt; compruébalo en tu propio Chrome (DevTools → Application, o el candado de la barra de direcciones).

3Cámara con getUserMedia

navigator.mediaDevices.getUserMedia(constraints) devuelve una promesa que se resuelve con un MediaStream: un flujo con una o más pistas (MediaStreamTrack), una por cada cámara o micrófono. Ese flujo se conecta a un <video> con srcObject y se ve en vivo. Las constraints son las condiciones que le pides al hardware:

dispositivo.js
export function abrirCamara(facingMode = "environment") {
  return navigator.mediaDevices.getUserMedia({
    video: {
      facingMode: { ideal: facingMode },   // "user" = frontal, "environment" = trasera
      width:  { ideal: 1280 },
      height: { ideal: 720 },
    },
    audio: false,
  });
}

ideal contra exact. Con ideal le dices "prefiero esto": si no existe, el navegador usa lo más parecido. Con exact (o min/max) es obligatorio: si no se puede cumplir, la promesa se rechaza con OverconstrainedError. En una app para estudiantes, casi siempre quieres ideal — un portátil no tiene cámara trasera, y no por eso la función debe fallar.

Mostrarla y, sobre todo, soltarla

app.js
// El permiso se pide AQUÍ, dentro del clic del usuario — no al cargar la página.
streamActual = await abrirCamara("environment");
videoEl.srcObject = streamActual;      // el <video> tiene autoplay y playsinline
dlgCamara.showModal();

// Al cerrar: detener CADA pista. Si no, el LED queda encendido y
// ninguna otra aplicación puede usar la cámara.
export function detenerCamara(stream) {
  stream?.getTracks().forEach((pista) => pista.stop());
}

El atributo playsinline del <video> evita que iOS lo abra a pantalla completa. Y no olvides el caso fácil de olvidar: si el usuario cierra el diálogo con la tecla Esc, el flujo también debe detenerse — por eso el checkpoint escucha el evento close del <dialog>.

dispositivo.js
export function describirErrorCamara(err) {
  switch (err?.name) {
    case "NotAllowedError":
      return "Bloqueaste el permiso de cámara. Habilítalo desde el candado de la barra de direcciones.";
    case "NotFoundError":
      return "Este dispositivo no tiene cámara disponible.";
    case "NotReadableError":
      return "La cámara está siendo usada por otra aplicación.";
    case "OverconstrainedError":
      return "La cámara no soporta la configuración pedida.";
    case "TypeError":
      return "La cámara solo funciona en HTTPS o en localhost.";
    default:
      return `No se pudo abrir la cámara (${err?.name ?? "error desconocido"}).`;
  }
}
Dos de estos mensajes se verificaron de verdad: el de NotAllowedError (permiso denegado, en la sección 8) y el de TypeError, borrando navigator.mediaDevices antes de cargar la página — que es justo lo que ve una página servida por HTTP.

4Del video a la foto: <canvas> y Blob

Un <video> no se puede "guardar" tal cual. Para tomar una foto se dibuja el fotograma actual en un <canvas> y se exporta a un Blob — un objeto binario que IndexedDB sabe guardar directamente (la Sesión 22 guardaba texto cifrado; hoy guardamos una imagen). Se reduce a un máximo de 640 px de ancho: una foto de teléfono puede pesar varios megabytes, y llenar IndexedDB de eso no tiene sentido para una miniatura.

dispositivo.js
export function capturarFoto(video, anchoMax = 640) {
  const escala = Math.min(1, anchoMax / video.videoWidth);
  const canvas = document.createElement("canvas");
  canvas.width  = Math.round(video.videoWidth  * escala);
  canvas.height = Math.round(video.videoHeight * escala);
  canvas.getContext("2d").drawImage(video, 0, 0, canvas.width, canvas.height);
  return new Promise((resolve) => canvas.toBlob(resolve, "image/jpeg", 0.8));
}

Para mostrar un Blob en pantalla se usa URL.createObjectURL(blob), que devuelve una URL temporal (blob:http://...). Esa URL ocupa memoria hasta que se libera con URL.revokeObjectURL() — por eso el checkpoint la libera cada vez que repinta la lista. Es el tipo de fuga que no se nota en una prueba corta y sí en una sesión de media hora.

5El micrófono: el mismo patrón, con otro hardware

El micrófono usa exactamente el mismo getUserMedia: solo cambia audio: true en vez de video. Mismo permiso, mismos errores, misma obligación de detener las pistas. Para ver que el micrófono funciona sin grabar nada, se conecta el flujo a un AnalyserNode de Web Audio, que entrega el volumen en cada instante:

dispositivo.js
export function abrirMicrofono() {
  return navigator.mediaDevices.getUserMedia({
    audio: { echoCancellation: true, noiseSuppression: true },
    video: false,
  });
}

export function crearMedidorDeNivel(stream) {
  const ctx = new AudioContext();
  ctx.resume();                       // llámalo dentro de un clic (política de autoplay)
  const analizador = ctx.createAnalyser();
  analizador.fftSize = 512;
  ctx.createMediaStreamSource(stream).connect(analizador);
  const datos = new Uint8Array(analizador.fftSize);
  return {
    leer() {                          // 0 = silencio, 1 = máximo
      analizador.getByteTimeDomainData(datos);
      let pico = 0;
      for (const v of datos) pico = Math.max(pico, Math.abs(v - 128));
      return pico / 128;
    },
    cerrar() { stream.getTracks().forEach((p) => p.stop()); ctx.close(); },
  };
}
Resultado real, con un micrófono falso de Chromium: durante 3 segundos, 30 lecturas del medidor dieron valores entre 0,00 y 0,05 (el dispositivo falso emite pitidos suaves), y al llamar cerrar() las pistas pasaron de 1 viva a 0 vivas — el micrófono se liberó. Con tu voz real los valores serán mucho mayores; en la Actividad 3 los mides tú.

6Ubicación con Geolocation

navigator.geolocation tiene dos formas de preguntar: getCurrentPosition() pide la posición una vez; watchPosition() avisa cada vez que cambia y devuelve un identificador que se cancela con clearWatch(). Las dos aceptan tres opciones:

enableHighAccuracy

Por defecto false. En true pide GPS: más preciso, más lento y con más batería. Con false el navegador puede usar Wi-Fi o red móvil.

timeout

Cuántos milisegundos esperar. Por defecto es infinito — siempre ponle un límite, o el usuario se queda esperando sin explicación.

maximumAge

Cuántos milisegundos de antigüedad aceptas en una posición ya conocida. Por defecto 0 (siempre una lectura nueva). Para una tarea, una posición de hace un minuto sirve.

coords.accuracy

La incertidumbre, en metros: "estoy aquí, con un margen de ±N m". Guárdala junto a la latitud y la longitud — sin ella, el dato engaña.

dispositivo.js
export function obtenerUbicacion({ altaPrecision = false, timeoutMs = 10000 } = {}) {
  return new Promise((resolve, reject) => {
    if (!("geolocation" in navigator)) {
      reject({ code: 0, message: "Geolocation no disponible" });
      return;
    }
    navigator.geolocation.getCurrentPosition(
      (pos) => resolve({
        lat: pos.coords.latitude,
        lon: pos.coords.longitude,
        precision: Math.round(pos.coords.accuracy),
        momento: new Date(pos.timestamp).toISOString(),
      }),
      reject,
      { enableHighAccuracy: altaPrecision, timeout: timeoutMs, maximumAge: 60000 }
    );
  });
}

export function describirErrorUbicacion(err) {
  switch (err?.code) {
    case 1: return "Denegaste el permiso de ubicación. La tarea sigue funcionando sin ella.";
    case 2: return "No se pudo determinar la posición (sin señal GPS o de red).";
    case 3: return "La ubicación tardó demasiado en responder. Intenta de nuevo.";
    default: return "La ubicación no está disponible en este navegador.";
  }
}

Los tres códigos de error son: 1 PERMISSION_DENIED (el usuario dijo no), 2 POSITION_UNAVAILABLE (no se pudo calcular: sin señal) y 3 TIMEOUT (se acabó el timeout). A diferencia de getUserMedia, Geolocation no usa nombres sino números — el switch sobre err.code es el equivalente.

7Privacidad: pedir lo mínimo, en el momento justo

Una foto y una ubicación son datos personales. Que el navegador pregunte no te exime de diseñar con cuidado; estas reglas son las que distinguen una app respetuosa de una que el usuario desinstala:

  • Pide cuando el usuario lo quiere. El botón "📍 Ubicación" pide la posición; nada la pide al abrir la app.
  • Que negar no rompa nada. Si el usuario dice no, la tarea se guarda igual, con un mensaje claro. Un permiso denegado casi nunca se recupera, así que la app debe sobrevivir sin él.
  • Guarda lo mínimo y dónde corresponde. En este proyecto la foto y la ubicación se quedan en el dispositivo (IndexedDB) y no viajan a ningún servidor; si algún día lo hicieran, el usuario debe saberlo antes.
  • Libera el hardware. Una cámara abierta que nadie usa es un problema de privacidad (LED encendido) y de batería.
  • Mira el marco legal. En Colombia, el tratamiento de datos personales está regulado por la Ley 1581 de 2012 (habeas data); si una app real guarda ubicación o fotos de personas, hay obligaciones de autorización y finalidad. Esto es una orientación para investigar, no asesoría legal.

8Caso real: tareas con foto y ubicación

El Gestor de Tareas ahora permite adjuntar a cada tarea una foto y una ubicación. Cuatro decisiones de diseño que vale la pena mirar con calma:

  • No hizo falta migrar la base de datos. Los campos nuevos (foto, ubicacion) no llevan índice, así que el esquema de IndexedDB (VERSION_DB = 1) no cambia — a diferencia de la migración que vimos en la Sesión 22. IndexedDB guarda objetos con la forma que tengan; el esquema solo cuenta para stores e índices.
  • Un único <dialog> de cámara compartido por todas las tareas, en vez de un video por tarea: una sola cámara abierta a la vez.
  • El permiso se pide dentro del clic del botón de cada tarea.
  • Las miniaturas liberan su URL con revokeObjectURL en cada repintado.

Esto no es lo que "debería" pasar — es lo que pasó al correr el checkpoint de hoy en Chromium con una cámara falsa, ubicación simulada en Tunja (5.5353, −73.3678, precisión 20 m) y los permisos en cada estado. La salida es literal:

Qué demuestra esa salida: (1) la cámara abre a 1280×720 y, al capturar, el diálogo se cierra y el flujo se detiene; (2) la foto se guarda como image/jpeg en IndexedDB y sigue ahí después de recargar, igual que la ubicación; (3) con el permiso denegado la app no se rompe — muestra el mensaje y sigue. Con una cámara real la foto pesará bastante más que los 5,9 kB de esta prueba: el dispositivo falso de Chromium produce una imagen sintética simple, así que mide el tamaño en tu teléfono (DevTools → Application → IndexedDB).
Lo que esta prueba NO cubre: una cámara ni un GPS reales. Chromium simula ambos; el comportamiento con hardware real (lentitud del GPS en interiores, la cámara trasera de un teléfono) solo lo puedes comprobar tú, en un dispositivo. De eso trata la sección siguiente.

9Probar en un teléfono real

En tu computador, http://localhost es contexto seguro, así que todo funciona. En un teléfono, http://192.168.x.x:8080 no lo es, y la cámara no se abrirá. Tres caminos para llegar a HTTPS (no los probé desde este entorno, pues requieren un teléfono físico — verifícalos tú):

  • Publicar en GitHub Pages. Ya tienes un repositorio por equipo; Pages sirve por HTTPS. Es lo más simple y se parece más a producción.
  • Reenviar el puerto por USB (Android + Chrome). Con la depuración USB activada, chrome://inspect permite reenviar un puerto del computador al teléfono; así el teléfono ve localhost:8080 y eso sí es contexto seguro.
  • Un túnel HTTPS temporal (herramientas como ngrok o cloudflared exponen tu servidor local con una URL https://). Útil para una demo; la URL cambia y es pública mientras esté activa, así que no dejes datos reales.

Resumen de la sesión

  • Las APIs de dispositivo exigen contexto seguro (HTTPS o localhost), permiso del usuario y un momento adecuado; los estados posibles son granted, denied y prompt, y se consultan sin avisos con la Permissions API.
  • getUserMedia sirve cámara y micrófono; ideal flexibiliza, exact obliga; siempre se detienen las pistas al terminar.
  • Una foto es un fotograma dibujado en <canvas> y exportado a Blob; las URLs de objeto se liberan con revokeObjectURL.
  • Geolocation tiene getCurrentPosition (una vez) y watchPosition (cada cambio); la precisión viene en metros y debe guardarse con las coordenadas.
  • Los errores y la negativa del usuario son flujo normal: mensajes claros y una app que sigue funcionando.
  • Verificado en Chromium con cámara y ubicación simuladas: abrir, capturar, guardar, recargar y los dos permisos denegados. El hardware real queda por probar en un teléfono.
