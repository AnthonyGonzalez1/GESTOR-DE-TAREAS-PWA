Notificaciones push y sincronización en segundo plano

Hasta hoy el Gestor solo hacía algo mientras alguien miraba la pestaña. Hoy aprende a hablarle al usuario —con avisos, y con push desde un servidor— y a terminar trabajo cuando ya no hay red ni pestaña abierta. Es también la sesión en que volvemos a InjectManifest de Workbox para escribir lógica propia dentro del Service Worker, y en que aprendemos a distinguir lo que sí pudimos probar de lo que no.

Objetivos de aprendizaje

  • ✓Distinguir la Notification API, la Push API y Background Sync: qué promete cada una, qué necesita y en qué navegadores existe.
  • ✓Pedir el permiso de notificaciones en contexto y mostrar avisos desde el Service Worker, con su clic.
  • ✓Pasar de generateSW a InjectManifest para escribir lógica propia dentro del Service Worker sin perder el precaché de Workbox.
  • ✓Construir una bandeja de salida con Background Sync que sobreviva a la falta de red, a los reintentos y a los envíos duplicados.
  • ✓Explicar qué parte del flujo de push se verificó aquí y cuál no se puede verificar sin un servicio de push real.

Recursos de esta sesión

1Tres APIs, tres promesas distintas

Hasta ahora el Gestor solo hacía algo cuando el usuario tenía la pestaña abierta. Hoy se vuelve capaz de hablarle al usuario y de terminar trabajo cuando él ya no está mirando. Eso lo reparten tres APIs que se confunden con facilidad porque suelen aparecer juntas, pero que resuelven problemas distintos:

APIQué hace¿Necesita servidor?¿Funciona con la app cerrada?Soporte (según MDN)
Notification APIMuestra una notificación del sistemaNoSolo si algo la dispara (p. ej. un push)Amplio
Push APIRecibe un mensaje que el servidor envía cuando quiereSí, con claves VAPID y un servicio de push del navegadorSí: el navegador despierta al Service WorkerChromium y Firefox; Safari en iOS solo para apps añadidas a la pantalla de inicio (documentación de Apple, no probado aquí)
Background SyncPospone un envío hasta que haya red, aunque se cierre la pestañaPara recibir lo que se envía, síSíSolo Chromium (Chrome, Edge). Ni Safari ni Firefox
La columna de soporte resume las páginas de MDN consultadas para esta sesión; el soporte cambia con las versiones, así que antes de depender de una API de producción conviene revisar la tabla vigente.
Qué se pudo y qué no se pudo comprobar hoy. Todo el código de esta guía se ejecutó en Chromium con Playwright. Se verificó de verdad: la notificación local, el manejador de push del Service Worker (con un mensaje inyectado), el clic en la notificación, la bandeja de salida con Background Sync y su plan B, y —por separado— que el servidor firma con VAPID y cifra el mensaje correctamente. No se pudo verificar la entrega real a través del servicio de push de Google: el entorno de pruebas no tiene acceso a esos servidores. Cada sección dice con exactitud en cuál de los dos grupos está lo que se muestra.

2Notificaciones: pedir permiso con contexto

Una notificación es una interrupción en el dispositivo del usuario, y el navegador no la permite sin su consentimiento. Notification.permission devuelve "default" (todavía no se le preguntó), "granted" o "denied". (La Permissions API usa el nombre prompt para el primer estado; son el mismo concepto con dos nombres.) Las reglas son las mismas de la Sesión 24:

  • Nunca al cargar la página. Se pide dentro del clic de un botón («🔔 Activar avisos») que explica para qué sirve.
  • denied es casi definitivo. Desde el código no se puede volver a preguntar; el usuario tiene que cambiarlo en la configuración del sitio. Por eso conviene no gastar la única oportunidad en un momento absurdo.
  • La app debe funcionar igual sin el permiso. Los avisos son un añadido, no la única vía.
notificaciones.js (fragmento)
/** Pedir permiso. Solo llamar desde un gesto del usuario. */
export async function pedirPermisoNotificaciones() {
  if (!("Notification" in window)) return "no-soportado";
  return Notification.requestPermission();
}
notificaciones.js (fragmento)
/** Notificación LOCAL (sin servidor): la muestra el propio SW.
 *  Se usa registration.showNotification y no `new Notification()` porque este
 *  último lanza TypeError en Chrome para Android. */
export async function mostrarAvisoLocal(titulo, cuerpo, url = "/index.html") {
  const reg = await navigator.serviceWorker.ready;
  await reg.showNotification(titulo, {
    body: cuerpo,
    icon: "/icons/icon-192.png",
    tag: "gestor-aviso",
    data: { url },
  });
}

Dos decisiones del segundo fragmento merecen explicación. Primero, la notificación la muestra registration.showNotification(), no new Notification(): según MDN, el constructor lanza TypeError en Chrome para Android, y además solo showNotification funciona cuando la página está cerrada. Segundo, las opciones: tag hace que una notificación con la misma etiqueta reemplace a la anterior en lugar de apilarse, y data viaja con la notificación hasta el momento del clic.

app.js (fragmento)
btnAvisos.addEventListener("click", async () => {
  // Permiso pedido AQUÍ, dentro del clic — y el usuario ya sabe para qué lo pulsó.
  const permiso = await pedirPermisoNotificaciones();
  if (permiso === "granted") {
    await mostrarAvisoLocal("Avisos activados", "Así se verán las notificaciones del Gestor.");
  } else {
    avisar("No se activaron los avisos. La app sigue funcionando igual.");
  }
  await pintarEstadoAvisos();
});

3De generateSW a InjectManifest

En la Sesión 23, Workbox generaba el Service Worker completo a partir de una receta (generateSW). Eso es cómodo mientras lo que necesitas es precaché y rutas. Pero un manejador de push, un notificationclick o un sync son lógica tuya, y una receta de configuración no sabe escribirlos. Con InjectManifest el reparto se invierte: tú escribes el Service Worker (sw-propio.js) y Workbox solo hace lo que nadie quiere hacer a mano: calcular la lista de archivos con sus hashes y pegarla donde tú indiques.

workbox-config.js
module.exports = {
  globDirectory: '.',
  globPatterns: [
    'index.html',
    'manifest.json',
    'css/*.css',
    '*.js',
    'icons/*.png',
  ],
  // sw-propio.js es el CÓDIGO FUENTE del SW: no debe precachearse a sí mismo.
  globIgnores: ['node_modules/**/*', 'servidor/**/*', 'lib/**/*', 'workbox-config.js', 'sw.js', 'sw-propio.js', 'package*.json'],
  swSrc: 'sw-propio.js',
  swDest: 'sw.js',
};

Fíjate en globIgnores: incluye a sw-propio.js. Es el código fuente del Service Worker; si entrara en la lista de precaché, el SW se precachearía a sí mismo. Y el archivo que el navegador registra sigue siendo sw.js —el que sale del comando—, así que app.js no cambia.

sw-propio.js (arranque)
// Workbox cargado desde archivos LOCALES (carpeta lib/), no desde un CDN:
// así el SW arranca igual sin conexión.
importScripts("lib/workbox-v7.4.1/workbox-sw.js");
workbox.setConfig({ modulePathPrefix: "lib/workbox-v7.4.1/", debug: false });

// IMPORTANTE: leer TODOS los módulos aquí, en el nivel superior. Cada acceso
// (workbox.precaching, workbox.routing…) dispara un importScripts, y
// importScripts solo se permite mientras el SW se está instalando/evaluando.
const { precacheAndRoute, cleanupOutdatedCaches } = workbox.precaching;
const { registerRoute } = workbox.routing;
const { CacheFirst, NetworkFirst } = workbox.strategies;
const { ExpirationPlugin } = workbox.expiration;

self.skipWaiting();
workbox.core.clientsClaim();
cleanupOutdatedCaches();
precacheAndRoute(self.__WB_MANIFEST); // ← aquí Workbox inyecta la lista

registerRoute(
  ({ url }) => url.pathname.startsWith("/icons/"),
  new CacheFirst({
    cacheName: "imagenes",
    plugins: [new ExpirationPlugin({ maxEntries: 20, maxAgeSeconds: 60 * 60 * 24 * 30 })],
  })
);
registerRoute(({ url }) => url.pathname.startsWith("/api/"), new NetworkFirst({ cacheName: "api-tareas" }));

Tres detalles que costaron tiempo al construir el ejemplo, y que conviene saber de antemano:

  • Workbox desde archivos locales, no desde un CDN. El comando npx workbox-cli copyLibraries lib copia las bibliotecas a lib/. Así el Service Worker arranca igual sin conexión. (De la carpeta copiada se dejaron solo los seis módulos que se usan: pasó de 1,8 MB a unos 28 KB.)
  • Los módulos se leen en el nivel superior. Cada acceso a workbox.precaching, workbox.routing… dispara un importScripts, y importScripts solo está permitido mientras el Service Worker se evalúa o instala. Si lees workbox.strategies dentro de un evento, falla.
  • El marcador debe aparecer una sola vez. Mi primer comando falló con Please ensure that your 'swSrc' file contains only one match for the following: self.__WB_MANIFEST… porque yo mismo había escrito ese texto en un comentario. Workbox busca el texto, no entiende de comentarios.
$ npx workbox-cli injectManifest workbox-config.js
The service worker file was written to sw.js
The service worker will precache 14 URLs, totaling 57 kB.

La regla de oro no cambia: cada vez que modifiques sw-propio.js o cualquier archivo precacheado, vuelve a correr el comando. Si no, el navegador seguirá sirviendo el sw.js viejo con las sumas de verificación viejas.

4Push: cómo viaja un mensaje desde el servidor

El navegador no deja que un servidor lo llame directamente: casi ningún teléfono tiene una dirección pública. En su lugar, cada navegador mantiene una conexión permanente con su propio servicio de push (Chrome usa los servidores de Google; Firefox, los de Mozilla). Tu servidor solo habla con ese intermediario:

Flujo de un push
1. La página pide permiso y llama pushManager.subscribe({ applicationServerKey: CLAVE_PÚBLICA_VAPID })
2. El servicio de push responde con una SUSCRIPCIÓN: { endpoint, keys: { p256dh, auth } }
3. La página envía esa suscripción a TU servidor (POST /api/suscribir) y él la guarda
4. Cuando quiere avisar, tu servidor firma una petición con su clave PRIVADA VAPID,
   cifra el mensaje con las claves de la suscripción y hace POST al endpoint
5. El servicio de push entrega el mensaje al navegador, que despierta al Service Worker
6. El evento "push" del SW muestra la notificación

VAPID es la identidad de tu servidor: un par de claves. La pública se le entrega al navegador al suscribir; la privada firma cada envío para que el servicio de push sepa que el mensaje viene de quien dice. El mensaje viaja cifrado de extremo a extremo (el intermediario no puede leerlo), con un límite de unos 4 KB. La clave privada nunca sale del servidor ni se sube a Git.

En la página: suscribirse

notificaciones.js (fragmento)
/** La clave pública VAPID llega en base64url; PushManager la quiere en bytes. */
export function urlBase64ABytes(base64url) {
  const relleno = "=".repeat((4 - (base64url.length % 4)) % 4);
  const b64 = (base64url + relleno).replace(/-/g, "+").replace(/_/g, "/");
  const binario = atob(b64);
  return Uint8Array.from(binario, (c) => c.charCodeAt(0));
}
notificaciones.js (fragmento)
/** Suscribe este navegador a push y envía la suscripción al servidor. */
export async function suscribirAPush() {
  const reg = await navigator.serviceWorker.ready;
  if (!("pushManager" in reg)) throw new Error("push-no-soportado");
  const { clave } = await (await fetch("/api/clave-publica")).json();
  const suscripcion = await reg.pushManager.subscribe({
    userVisibleOnly: true, // obligatorio: cada push debe mostrar una notificación
    applicationServerKey: urlBase64ABytes(clave),
  });
  const resp = await fetch("/api/suscribir", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(suscripcion.toJSON()),
  });
  if (!resp.ok) throw new Error("El servidor no guardó la suscripción (" + resp.status + ")");
  return suscripcion;
}

userVisibleOnly: true es obligatorio en Chrome y es un compromiso: cada push que llegue debe terminar en una notificación visible. Por eso el manejador del Service Worker mete showNotification dentro de event.waitUntil(): si el SW termina sin mostrar nada, Chrome muestra por ti una notificación genérica («este sitio se actualizó en segundo plano») y, si se repite, puede revocar el permiso (comportamiento documentado por Google; no lo provoqué en la prueba).

En el Service Worker: recibir y mostrar

sw-propio.js (push)
// ── Push: llega un mensaje del servidor aunque la app esté cerrada ─────────
self.addEventListener("push", (event) => {
  let datos = { titulo: "Gestor de Tareas", cuerpo: "Tienes novedades.", url: "/index.html" };
  try {
    if (event.data) datos = { ...datos, ...event.data.json() };
  } catch {
    if (event.data) datos.cuerpo = event.data.text(); // el mensaje no era JSON
  }
  // userVisibleOnly:true (al suscribir) OBLIGA a mostrar una notificación en
  // cada push; por eso va dentro de waitUntil, siempre.
  event.waitUntil(
    self.registration.showNotification(datos.titulo, {
      body: datos.cuerpo,
      icon: "/icons/icon-192.png",
      badge: "/icons/icon-192.png",
      tag: datos.tag ?? "gestor-aviso", // misma etiqueta = reemplaza, no apila
      data: { url: datos.url },
    })
  );
});

El try/catch no es adorno: un push puede traer JSON, texto plano o nada. Un manejador que lanza una excepción con un mensaje inesperado termina sin notificación, y eso viola el compromiso de userVisibleOnly.

En el servidor: firmar, cifrar y enviar

El servidor de ejemplo (carpeta servidor/, unas 140 líneas) usa solo el módulo http de Node y la biblioteca web-push. Hace tres cosas: servir los archivos del Gestor, gestionar suscripciones y push, y recibir las tareas del Background Sync. Es código de enseñanza: sin autenticación, sin base de datos real, sin HTTPS. Las partes de push:

servidor/server.js (claves VAPID)
// ── Claves VAPID: identifican a TU servidor ante el servicio de push ────────
// Se generan una sola vez y se guardan. La PRIVADA no sale nunca de este
// archivo (y no se sube a Git); la PÚBLICA sí se entrega al navegador.
let claves;
if (fs.existsSync(ARCHIVO_CLAVES)) {
  claves = JSON.parse(fs.readFileSync(ARCHIVO_CLAVES, "utf8"));
} else {
  claves = webpush.generateVAPIDKeys();
  fs.writeFileSync(ARCHIVO_CLAVES, JSON.stringify(claves, null, 2));
  console.log("Claves VAPID generadas en claves-vapid.json");
}
// El "subject" debe ser un mailto: o una URL tuya; el servicio de push lo usa para contactarte.
webpush.setVapidDetails("mailto:tu-correo@ejemplo.com", claves.publicKey, claves.privateKey);
servidor/server.js (enviar)
  if (req.method === "POST" && ruta === "/api/enviar-prueba") {
    const { titulo = "Gestor de Tareas", cuerpo = "Mensaje de prueba desde el servidor", url = "/index.html" } = await leerCuerpo(req);
    const mensaje = JSON.stringify({ titulo, cuerpo, url });
    const resultado = { enviados: 0, fallidos: 0, eliminadas: 0 };
    for (const sub of [...datos.suscripciones]) {
      try {
        await webpush.sendNotification(sub, mensaje, { TTL: 60 });
        resultado.enviados++;
      } catch (err) {
        resultado.fallidos++;
        // 404/410: la suscripción ya no existe (el usuario revocó el permiso o
        // desinstaló). Hay que borrarla, o se acumulan suscripciones muertas.
        if (err.statusCode === 404 || err.statusCode === 410) {
          datos.suscripciones = datos.suscripciones.filter((s) => s.endpoint !== sub.endpoint);
          resultado.eliminadas++;
        } else {
          console.error("Error al enviar push:", err.statusCode ?? "", err.message);
        }
      }
    }
    guardarDatos(datos);
    return responder(res, 200, resultado);
  }

Observa el manejo de 404 y 410: significan «esta suscripción ya no existe» (el usuario revocó el permiso, desinstaló o el navegador la caducó). Hay que borrarla, o el servidor seguirá enviando a destinatarios muertos para siempre.

5El clic en la notificación

Una notificación que no hace nada al tocarla es una molestia. El evento notificationclick ocurre en el Service Worker (la página puede estar cerrada), y lo habitual es: cerrar la notificación, buscar una ventana de la app ya abierta y enfocarla, y solo si no hay ninguna, abrir una nueva.

sw-propio.js (clic)
// ── Clic en la notificación: enfocar la app abierta, o abrirla ─────────────
self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const destino = new URL(event.notification.data?.url ?? "/index.html", self.location.origin).href;
  event.waitUntil(
    (async () => {
      const ventanas = await clients.matchAll({ type: "window", includeUncontrolled: true });
      const abierta = ventanas.find((v) => new URL(v.url).origin === self.location.origin);
      if (abierta) return abierta.focus();
      return clients.openWindow(destino);
    })()
  );
});

La dirección de destino viaja en data.url, que se fijó al mostrar la notificación. Así un aviso de «Tareas sincronizadas» y uno de «Recordatorio» pueden llevar a lugares distintos con el mismo manejador.

6Background Sync: la bandeja de salida

Hasta aquí el Gestor guarda todo en el dispositivo (IndexedDB), pero nunca lo envía a ninguna parte. Hoy cada tarea nueva también debe llegar a un servidor, sin que la acción del usuario dependa de la red. El patrón se llama bandeja de salida (outbox):

  1. La tarea se guarda en IndexedDB como siempre y se pinta en pantalla.
  2. Además se anota un «cambio pendiente» en un almacén nuevo, outbox.
  3. Se le pide al navegador una sincronización: registration.sync.register("sync-tareas").
  4. Cuando el navegador considera que hay red, despierta al Service Worker con el evento sync, y este envía lo que haya en la bandeja y borra lo que se confirmó.

Nueva versión de la base de datos

El almacén outbox no existe en la base de la Sesión 22. Agregarlo exige subir VERSION_DB a 2 y escribir la migración por tramos, de modo que quien ya tenía la versión 1 conserve sus tareas y quien instala por primera vez ejecute ambos tramos:

db.js (migración)
    peticion.onupgradeneeded = (event) => {
      const db = event.target.result;
      // Las migraciones se escriben por TRAMOS según la versión de la que se
      // viene (Sesión 22): quien ya tenía la v1 conserva sus tareas y solo
      // recibe lo nuevo; quien instala por primera vez ejecuta ambos tramos.
      if (event.oldVersion < 1) {
        const store = db.createObjectStore("tareas", { keyPath: "id", autoIncrement: true });
        store.createIndex("porPrioridad", "prioridad", { unique: false });
        store.createIndex("porTitulo", "titulo", { unique: true });
      }
      if (event.oldVersion < 2) {
        // La clave es un UUID que genera la app (no autoIncrement): el servidor
        // lo usa para no duplicar un cambio si el envío se reintenta.
        db.createObjectStore("outbox", { keyPath: "idCambio" });
      }
    };

La clave del almacén es un UUID que genera la app (keyPath: "idCambio"), no un número automático. Se verá enseguida por qué.

En la página: anotar y pedir la sincronización

sync.js (fragmento)
/** Anota un cambio pendiente. Devuelve el idCambio (UUID). */
export function encolarCambio(db, tipo, datos) {
  const cambio = { idCambio: crypto.randomUUID(), tipo, datos, creadoEn: Date.now() };
  return new Promise((resolve, reject) => {
    const tx = db.transaction("outbox", "readwrite");
    tx.objectStore("outbox").add(cambio);
    tx.oncomplete = () => resolve(cambio.idCambio);
    tx.onerror = () => reject(tx.error);
  });
}
sync.js (fragmento)
/** Pide la sincronización. Devuelve "segundo-plano" si el navegador se encargará
 *  (aunque cierres la pestaña) o "desde-la-pagina" si hubo que enviarla aquí
 *  (puede lanzar si el servidor no responde: la entrada sigue en la bandeja). */
export async function pedirSincronizacion(db) {
  if (haySyncEnSegundoPlano()) {
    try {
      const reg = await navigator.serviceWorker.ready;
      await reg.sync.register(ETIQUETA); // registrar dos veces la misma etiqueta = una sola tarea
      return "segundo-plano";
    } catch {
      // Tener SyncManager no basta: register() falla (NotAllowedError) si el
      // usuario bloqueó la sincronización en segundo plano para este sitio.
    }
  }
  // Plan B (Safari, Firefox, o permiso bloqueado): solo funciona mientras la pestaña siga abierta.
  await vaciarDesdeLaPagina(db);
  return "desde-la-pagina";
}

Hay dos razones para caer al plan B, no una. La primera es obvia: Safari y Firefox no tienen SyncManager. La segunda se descubrió al probar: aun teniéndolo, register() lanza NotAllowedError si el permiso de sincronización en segundo plano está bloqueado para el sitio. El catch convierte ese fallo en el mismo plan B, en vez de dejar la tarea pendiente para siempre.

En el Service Worker: el evento sync

sw-propio.js (sincronización)
async function vaciarBandeja() {
  const db = await abrirDB();
  const pendientes = await pedir(db.transaction("outbox").objectStore("outbox").getAll());
  let enviados = 0;
  for (const cambio of pendientes) {
    const resp = await fetch("/api/tareas", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(cambio),
    });
    // Si falla, lanzamos: el navegador reintentará (con espera creciente).
    if (!resp.ok) throw new Error("El servidor respondió " + resp.status);
    // Se borra cada entrada apenas se confirma, no al final: si el siguiente
    // falla, no se reenvía lo que ya llegó.
    await pedir(db.transaction("outbox", "readwrite").objectStore("outbox").delete(cambio.idCambio));
    enviados++;
  }
  db.close();
  return enviados;
}
sw-propio.js (evento)
self.addEventListener("sync", (event) => {
  if (event.tag === "sync-tareas") {
    event.waitUntil(vaciarBandeja().then(avisarDeSincronizacion));
  }
});

Cuatro decisiones de diseño, cada una con una razón:

  • Lanzar para reintentar. Si fetch falla o el servidor responde con error, el manejador lanza una excepción. Esa promesa rechazada es la señal para que el navegador programe otro intento más tarde, con esperas cada vez mayores. El navegador decide cuántos intentos y cuándo; no es un servicio garantizado.
  • Borrar cada entrada apenas se confirma, no al final. Si la tercera falla, las dos primeras no se reenvían en el reintento.
  • Idempotencia. Aun así, un envío puede llegar al servidor y que la respuesta se pierda: el SW cree que falló y reenvía. Por eso cada cambio lleva su UUID y el servidor ignora los repetidos ("duplicado": true en la salida de abajo). Sin esto, un reintento duplica tareas.
  • Avisar por notificación solo si nadie mira. Si hay una ventana visible, basta con un mensaje en pantalla; la notificación del sistema se reserva para cuando el usuario no está en la app.

  await actualizarEstadoSync();
});

La línea de estado (☁ Todo sincronizado… / ☁ 1 cambio(s) pendiente(s)…) cuenta lo que hay en la bandeja. Un sistema que acepta trabajo «para después» sin mostrar qué quedó pendiente es un sistema en el que nadie confía.

B) SW controla la página: true | cachés: precaché con 14 entradas

Qué demuestra: (1) la migración conserva los datos de la versión 1 y crea outbox; (2) una tarea creada sin conexión queda anotada y visible como pendiente; (3) al dispararse el evento sync llega al servidor y la bandeja se vacía; (4) un reenvío del mismo cambio no se duplica; (5) si el servidor está caído, la entrada no se pierde y llega cuando vuelve; (6) sin SyncManager, o con el permiso bloqueado, el plan B envía desde la página.
Dos cosas que esta prueba no es. (1) El evento sync se disparó con ServiceWorker.dispatchSyncEvent, el mismo mecanismo que usa el botón Sync del panel Application → Background Sync de las DevTools. Cinco segundos después de «volver la red» el navegador no había reintentado por su cuenta: sus reintentos automáticos se espacian en minutos y no medí cuánto. (2) «Sin conexión» se simuló apagando el servidor y activando el modo sin red en la página; no se cortó la conexión de un dispositivo real.

Notificaciones, push y clic

$ node test_s26.js (continuación)
B) permiso inicial: default | Avisos sin activar.
B) notificaciones tras activar avisos: [{"title":"Avisos activados","tag":"gestor-aviso","url":"/index.html"}]
B) tras push inyectado (JSON): + {"title":"Recordatorio","body":"Tienes 2 tareas pendientes","tag":"recordatorio","url":"/index.html?desde=push"}
B) tras push con texto plano: {"title":"Gestor de Tareas","body":"texto plano, no JSON","tag":"gestor-aviso"} (reemplazó a «Avisos activados»: misma tag)
B) tras 2º push, misma tag «recordatorio»: body "Ahora son 3" (reemplazó al anterior, no se apiló)
B) notificationclick → {"habia":1,"quedan":0} (la notificación se cierra)
B) sin ventanas visibles (simulado) → [{"title":"Tareas sincronizadas","body":"2 tareas llegaron al servidor."}]
B) con la ventana visible → notificaciones gestor-sync: 0
Qué demuestra: el manejador de push muestra la notificación tanto con JSON como con texto plano; tag reemplaza en vez de apilar; el clic cierra la notificación; y la notificación de sincronización solo aparece cuando no hay ventana visible.
Cómo se inyectó cada cosa, sin esconder nada. El push se entregó con ServiceWorker.deliverPushMessage de CDP, que equivale al botón Push de Application → Service Workers: se salta el servicio de push, así que prueba nuestro manejador pero no la entrega real. El clic se simuló despachando un NotificationEvent dentro del Service Worker: no se tocó una notificación de verdad. Y «sin ventanas visibles» se simuló reemplazando clients.matchAll dentro del SW, porque Chromium sin pantalla siempre considera visible la página.

El intento de suscripción real

B) intento de suscripción push real → aviso: "El servicio de push del navegador no respondió (¿sin red, o navegador sin servicio de push?)."
console: Chrome currently does not support the Push API in incognito mode (https://crbug.com/401439)…

Esto no es un éxito: el subscribe() real falló. El contexto de Playwright es equivalente a una ventana de incógnito, donde Chrome no soporta Push. Lo intenté también en un perfil persistente: el navegador intentó conectar con servidores de Google (android.clients.google.com, accounts.google.com), el entorno denegó esas conexiones y la prueba no llegó a terminar. Lo útil que sí deja el intento es que describirErrorPush tradujo el AbortError a un mensaje comprensible en vez de dejar la interfaz colgada.

El servidor, verificado por separado

Como no hay servicio de push, se verificó la parte del servidor contra un «servicio de push» falso: un servidor HTTPS local al que apunta una suscripción fabricada con claves propias. Así se puede ver exactamente lo que Chrome o Firefox recibirían, y descifrarlo con las claves del «navegador»:

$ node test_push_servidor.js
suscribir: {"status":201,"json":{"ok":true,"total":1}}
suscripción incompleta: {"status":400,"json":{"error":"suscripción incompleta"}}
enviar-prueba: {"status":200,"json":{"enviados":1,"fallidos":0,"eliminadas":0}}
cabeceras: {"content-encoding":"aes128gcm","ttl":"60","content-type":"application/octet-stream","authorization":"vapid t=<JWT>, k=<clave pública>"}
JWT VAPID: header {"typ":"JWT","alg":"ES256"} | claims {"aud":"https://localhost:3104","exp":…,"sub":"mailto:tu-correo@ejemplo.com"}
k == clave pública del servidor: true
firma ES256 del JWT válida: true
cuerpo descifrado con las claves del "navegador": {"titulo":"Recordatorio","cuerpo":"Tienes 2 tareas","url":"/index.html"}
bytes en la red: 175
con endpoint que responde 410: {"status":200,"json":{"enviados":0,"fallidos":1,"eliminadas":1}}

Qué demuestra: el servidor rechaza suscripciones incompletas; firma con VAPID (la firma ES256 verifica con la clave pública); cifra el mensaje con aes128gcm de modo que solo se lee con las claves de la suscripción; y elimina las suscripciones muertas cuando el servicio responde 410.
La cadena completa nunca se recorrió. Verificamos el manejador del SW con un push inyectado, y el servidor con un destinatario falso, pero no el eslabón del medio: que el servicio de push real de Google o Mozilla acepte esa petición y la entregue. Para ese eslabón, la única prueba válida es la tuya, en un navegador de escritorio normal (no incógnito) con acceso a Internet.

9Buen trato al usuario

  • Pide el permiso cuando el usuario entienda el beneficio, no en la primera visita. Una tasa baja de «Permitir» y un «Bloquear» casi irreversible son el costo de preguntar mal.
  • Pocos avisos, y que importen. Cada notificación innecesaria enseña al usuario a revocar el permiso de todas.
  • No pongas datos sensibles en el cuerpo del push. Viaja cifrado, pero termina en la pantalla de bloqueo, a la vista de cualquiera.
  • Ofrece cómo desactivarlo dentro de la app (el botón «Cancelar suscripción push» hace unsubscribe() y avisa al servidor).
  • Datos personales: una suscripción push identifica un dispositivo. En Colombia aplica la Ley 1581 de 2012 de protección de datos personales; esta guía solo la menciona como orientación y no es asesoría legal.

Resumen de la sesión

  • Notification, Push y Background Sync son tres promesas distintas: mostrar, recibir del servidor y enviar diferido. Solo Notification es amplia; Push exige servidor y servicio de push; Background Sync es solo de Chromium.
  • El permiso se pide dentro de un clic y con contexto; denied es casi definitivo; la app funciona igual sin él.
  • InjectManifest deja el Service Worker en tus manos y a Workbox solo la lista de precaché; el marcador debe aparecer una sola vez y el comando se reejecuta tras cada cambio.
  • Push: VAPID identifica al servidor, la suscripción identifica al dispositivo, el mensaje viaja cifrado, y userVisibleOnly obliga a mostrar siempre una notificación. Se borran las suscripciones que responden 404/410.
  • La bandeja de salida (outbox) hace que la acción del usuario nunca dependa de la red; lanzar una excepción pide reintento; el UUID por cambio evita duplicados; y hay plan B para Safari, Firefox y permiso bloqueado.
  • Verificado: notificaciones, manejador de push (con mensaje inyectado), clic, sincronización, reintento disparado a mano, migración, y el servidor por separado (VAPID y cifrado). No verificado: la entrega real por el servicio de push, un teléfono real, iOS, el reintento automático del navegador y la batería.
