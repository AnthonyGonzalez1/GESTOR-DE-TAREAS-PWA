SECCIÓN 01

Tres APIs, tres promesas distintas

Suelen aparecer juntas y se confunden con facilidad, pero resuelven problemas distintos.

Notification APIPush APIBackground Sync
Tres APIs · 1.1

Hablarle al usuario y terminar trabajo

Hasta ahora el Gestor solo hacía algo cuando el usuario tenía la pestaña abierta. Hoy se vuelve capaz de hablarle al usuario y de terminar trabajo cuando él ya no está mirando. Lo reparten tres APIs:

Notification API

Mostrar. Muestra una notificación del sistema. No necesita servidor.

Push API

Recibir. Recibe un mensaje que el servidor envía cuando quiere, incluso con la app cerrada.

Background Sync

Enviar diferido. Pospone un envío hasta que haya red, aunque se cierre la pestaña.

Qué se pudo y qué no se pudo comprobar hoy

Todo el código de esta guía se ejecutó en Chromium con Playwright.

SECCIÓN 02

Notificaciones: pedir permiso con contexto

Una notificación es una interrupción en el dispositivo del usuario, y el navegador no la permite sin su consentimiento.

Notification.permissionDentro de un clicAviso local
Permiso · 2.1

Tres estados y tres reglas

"default"Todavía no se le preguntó
"granted"El usuario aceptó
"denied"El usuario bloqueó

Notification.permission devuelve uno de estos tres valores. La Permissions API usa el nombre prompt para el primer estado; son el mismo concepto con dos nombres.

Las reglas son las mismas de la Sesión 24:

  • Nunca al cargar la página. Se pide dentro del clic de un botón («🔔 Activar avisos») que explica para qué sirve.
  • denied es casi definitivo. Desde el código no se puede volver a preguntar; el usuario tiene que cambiarlo en la configuración del sitio. Por eso conviene no gastar la única oportunidad en un momento absurdo.
  • La app debe funcionar igual sin el permiso. Los avisos son un añadido, no la única vía.
Permiso · 2.2

Pedir el permiso, dentro del clic

/** Pedir permiso. Solo llamar desde un gesto del usuario. */
export async function pedirPermisoNotificaciones() {
  if (!("Notification" in window)) return "no-soportado";
  return Notification.requestPermission();

app.js (fragmento)
btnAvisos.addEventListener("click", async () => {

Permiso · 2.3

Mostrar el aviso local: dos decisiones

notificaciones.js (fragmento)
/** Notificación LOCAL (sin servidor): la muestra el propio SW.
 *  Se usa registration.showNotification y no `new Notification()` porque este
 *  último lanza TypeError en Chrome para Android. */
export async function mostrarAvisoLocal(titulo, cuerpo, url = "/index.html") {
  const reg = await navigator.serviceWorker.ready;
  await reg.showNotification(titulo, {
    body: cuerpo,
    icon: "/icons/icon-192.png",
    tag: "gestor-aviso",
    data: { url },
  });
}
showNotification, no new Notification(): según MDN, el constructor lanza TypeError en Chrome para Android, y solo showNotification funciona con la página cerrada. tag y data: tag reemplaza una notificación con la misma etiqueta en vez de apilar; data viaja con la notificación hasta el clic.

SECCIÓN 04

Push: cómo viaja un mensaje desde el servidor

El navegador no deja que un servidor lo llame directamente: casi ningún teléfono tiene una dirección pública.

Servicio de pushVAPIDSuscripción
Push · 4.1

Un intermediario entre tu servidor y el navegador

Cada navegador mantiene una conexión permanente con su propio servicio de push (Chrome usa los servidores de Google; Firefox, los de Mozilla). Tu servidor solo habla con ese intermediario.

Push · 4.2

Los seis pasos, y quién es VAPID

Flujo de un push
1. La página pide permiso y llama pushManager.subscribe({ applicationServerKey: CLAVE_PÚBLICA_VAPID })
2. El servicio de push responde con una SUSCRIPCIÓN: { endpoint, keys: { p256dh, auth } }
3. La página envía esa suscripción a TU servidor (POST /api/suscribir) y él la guarda
4. Cuando quiere avisar, tu servidor firma una petición con su clave PRIVADA VAPID,
   cifra el mensaje con las claves de la suscripción y hace POST al endpoint
5. El servicio de push entrega el mensaje al navegador, que despierta al Service Worker
6. El evento "push" del SW muestra la notificación

VAPID

Es la identidad de tu servidor: un par de claves.

La clave pública

Se le entrega al navegador al suscribir.

La clave privada

Firma cada envío para que el servicio de push sepa que el mensaje viene de quien dice. Nunca sale del servidor ni se sube a Git.

El mensaje viaja cifrado de extremo a extremo (el intermediario no puede leerlo), con un límite de unos 4 KB.
Push · 4.3

En la página: la clave pública, en bytes

notificaciones.js (fragmento)
/** La clave pública VAPID llega en base64url; PushManager la quiere en bytes. */
export function urlBase64ABytes(base64url) {
  const relleno = "=".repeat((4 - (base64url.length % 4)) % 4);
  const b64 = (base64url + relleno).replace(/-/g, "+").replace(/_/g, "/");
  const binario = atob(b64);
  return Uint8Array.from(binario, (c) => c.charCodeAt(0));
}
El servidor entrega la clave pública VAPID en base64url; pushManager.subscribe la quiere como bytes. Esta función hace la conversión, y la usa suscribirAPush() en la lámina siguiente.
Push · 4.4

En la página: suscribirse

notificaciones.js (fragmento)
/** Suscribe este navegador a push y envía la suscripción al servidor. */
export async function suscribirAPush() {
  const reg = await navigator.serviceWorker.ready;
  if (!("pushManager" in reg)) throw new Error("push-no-soportado");
  const { clave } = await (await fetch("/api/clave-publica")).json();
  const suscripcion = await reg.pushManager.subscribe({
    userVisibleOnly: true, // obligatorio: cada push debe mostrar una notificación
    applicationServerKey: urlBase64ABytes(clave),
  });
  const resp = await fetch("/api/suscribir", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(suscripcion.toJSON()),
  });
  if (!resp.ok) throw new Error("El servidor no guardó la suscripción (" + resp.status + ")");
  return suscripcion;
}

Clic · 5.1

El clic en la notificación

Una notificación que no hace nada al tocarla es una molestia. El evento notificationclick ocurre en el Service Worker (la página puede estar cerrada), y lo habitual es:

1
CerrarSe cierra la notificación.
→
2
EnfocarSe busca una ventana de la app ya abierta y se enfoca.
→
3
AbrirSolo si no hay ninguna, se abre una nueva.
La dirección de destino viaja en data.url, que se fijó al mostrar la notificación. Así un aviso de «Tareas sincronizadas» y uno de «Recordatorio» pueden llevar a lugares distintos con el mismo manejador.
Clic · 5.2

sw-propio.js (clic)

sw-propio.js (clic)
// ── Clic en la notificación: enfocar la app abierta, o abrirla ─────────────
self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const destino = new URL(event.notification.data?.url ?? "/index.html", self.location.origin).href;
  event.waitUntil(
    (async () => {
      const ventanas = await clients.matchAll({ type: "window", includeUncontrolled: true });
      const abierta = ventanas.find((v) => new URL(v.url).origin === self.location.origin);
      if (abierta) return abierta.focus();
      return clients.openWindow(destino);
    })()
  );
});
clients.matchAll busca las ventanas; si hay una del mismo origen, se enfoca (focus()); si no, clients.openWindow(destino) abre una nueva.
SECCIÓN 06

Background Sync: la bandeja de salida

Hoy cada tarea nueva también debe llegar a un servidor, sin que la acción del usuario dependa de la red.

outboxsync-tareasidCambio
Sync · 6.1

La bandeja de salida: cuatro pasos

Hasta aquí el Gestor guarda todo en el dispositivo (IndexedDB), pero nunca lo envía a ninguna parte. El patrón se llama bandeja de salida (outbox):

1
GuardarLa tarea se guarda en IndexedDB como siempre y se pinta en pantalla.
→
2
AnotarSe anota un «cambio pendiente» en un almacén nuevo, outbox.
→
3
PedirSe le pide al navegador una sincronización: registration.sync.register("sync-tareas").
→
4
EnviarCuando el navegador considera que hay red, despierta al SW con el evento sync, que envía lo que haya en la bandeja y borra lo que se confirmó.
Sync · 6.2

Nueva versión de la base de datos

El almacén outbox no existe en la base de la Sesión 22: hay que subir VERSION_DB a 2 y migrar por tramos.

Sync · 6.3

En la página: anotar el cambio

sync.js (fragmento)
/** Anota un cambio pendiente. Devuelve el idCambio (UUID). */
export function encolarCambio(db, tipo, datos) {
  const cambio = { idCambio: crypto.randomUUID(), tipo, datos, creadoEn: Date.now() };
  return new Promise((resolve, reject) => {
    const tx = db.transaction("outbox", "readwrite");
    tx.objectStore("outbox").add(cambio);
    tx.oncomplete = () => resolve(cambio.idCambio);
    tx.onerror = () => reject(tx.error);
  });
}
Cada cambio lleva su UUID (crypto.randomUUID()), generado en el dispositivo. Más adelante, el servidor lo usa para ignorar los envíos repetidos.
Sync · 6.4

En la página: pedir la sincronización

sync.js (fragmento)
/** Pide la sincronización. Devuelve "segundo-plano" si el navegador se encargará
 *  (aunque cierres la pestaña) o "desde-la-pagina" si hubo que enviarla aquí
 *  (puede lanzar si el servidor no responde: la entrada sigue en la bandeja). */
export async function pedirSincronizacion(db) {
  if (haySyncEnSegundoPlano()) {
    try {
      const reg = await navigator.serviceWorker.ready;
      await reg.sync.register(ETIQUETA); // registrar dos veces la misma etiqueta = una sola tarea
      return "segundo-plano";
    } catch {
      // Tener SyncManager no basta: register() falla (NotAllowedError) si el
      // usuario bloqueó la sincronización en segundo plano para este sitio.
    }
  }
  // Plan B (Safari, Firefox, o permiso bloqueado): solo funciona mientras la pestaña siga abierta.
  await vaciarDesdeLaPagina(db);
  return "desde-la-pagina";
}
Sync · 6.5

Hay dos razones para caer al plan B, no una

1. No existe SyncManager

Es la razón obvia: Safari y Firefox no tienen SyncManager.

2. El permiso está bloqueado

Se descubrió al probar: aun teniendo SyncManager, register() lanza NotAllowedError si el permiso de sincronización en segundo plano está bloqueado para el sitio.

El catch convierte ese segundo fallo en el mismo plan B, en vez de dejar la tarea pendiente para siempre. El plan B solo funciona mientras la pestaña siga abierta.
Sync · 6.6

En el Service Worker: vaciar la bandeja (1/2)

sw-propio.js (sincronización, 1/2)
async function vaciarBandeja() {
  const db = await abrirDB();
  const pendientes = await pedir(db.transaction("outbox").objectStore("outbox").getAll());
  let enviados = 0;
  for (const cambio of pendientes) {
    const resp = await fetch("/api/tareas", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(cambio),
    });
    // Si falla, lanzamos: el navegador reintentará (con espera creciente).
    if (!resp.ok) throw new Error("El servidor respondió " + resp.status);
    // (continúa en la lámina siguiente)
Lanzar para reintentar. Si fetch falla o el servidor responde con error, el manejador lanza una excepción: esa promesa rechazada es la señal para que el navegador programe otro intento.

En el Service Worker: vaciar la bandeja (2/2)

sw-propio.js (sincronización, 2/2)
    // Se borra cada entrada apenas se confirma, no al final: si el siguiente
    // falla, no se reenvía lo que ya llegó.
    await pedir(db.transaction("outbox", "readwrite").objectStore("outbox").delete(cambio.idCambio));
    enviados++;
  }
  db.close();
  return enviados;
}
Borrar apenas se confirma, no al final. Si la tercera falla, las dos primeras no se reenvían en el reintento. Al terminar se cierra la base y se devuelve cuántos cambios se enviaron.
Sync · 6.7

El evento sync

sw-propio.js (evento)
self.addEventListener("sync", (event) => {
  if (event.tag === "sync-tareas") {
    event.waitUntil(vaciarBandeja().then(avisarDeSincronizacion));
  }
});
Si vaciarBandeja() lanza una excepción, la promesa que recibe event.waitUntil se rechaza. Esa promesa rechazada es la señal para que el navegador programe otro intento más tarde, con esperas cada vez mayores. El navegador decide cuántos intentos y cuándo; no es un servicio garantizado.
Sync · 6.8

Cuatro decisiones de diseño, cada una con su razón

1. Lanzar para reintentar

Si fetch falla o el servidor responde con error, el manejador lanza una excepción. Esa promesa rechazada es la señal para que el navegador programe otro intento.

2. Borrar apenas se confirma

No al final. Si la tercera falla, las dos primeras no se reenvían en el reintento.

3. Idempotencia

Un envío puede llegar y que la respuesta se pierda: el SW cree que falló y reenvía. Por eso cada cambio lleva su UUID y el servidor ignora los repetidos ("duplicado": true). Sin esto, un reintento duplica tareas.

4. Avisar solo si nadie mira

Si hay una ventana visible, basta con un mensaje en pantalla; la notificación del sistema se reserva para cuando el usuario no está en la app.

Buen trato

Buen trato al usuario

  • Pide el permiso cuando el usuario entienda el beneficio, no en la primera visita. Una tasa baja de «Permitir» y un «Bloquear» casi irreversible son el costo de preguntar mal.
  • Pocos avisos, y que importen. Cada notificación innecesaria enseña al usuario a revocar el permiso de todas.
  • No pongas datos sensibles en el cuerpo del push. Viaja cifrado, pero termina en la pantalla de bloqueo, a la vista de cualquiera.
  • Ofrece cómo desactivarlo dentro de la app (el botón «Cancelar suscripción push» hace unsubscribe() y avisa al servidor).
  • Datos personales: una suscripción push identifica un dispositivo. En Colombia aplica la Ley 1581 de 2012 de protección de datos personales; esta guía solo la menciona como orientación y no es asesoría legal.

Resumen de la sesión

  • Notification, Push y Background Sync son tres promesas distintas: mostrar, recibir del servidor y enviar diferido. Solo Notification es amplia; Push exige servidor y servicio de push; Background Sync es solo de Chromium.
  • El permiso se pide dentro de un clic y con contexto; denied es casi definitivo; la app funciona igual sin él.
  • InjectManifest deja el Service Worker en tus manos y a Workbox solo la lista de precaché; el marcador debe aparecer una sola vez y el comando se reejecuta tras cada cambio.
  • Push: VAPID identifica al servidor, la suscripción identifica al dispositivo, el mensaje viaja cifrado, y userVisibleOnly obliga a mostrar siempre una notificación. Se borran las suscripciones que responden 404/410.
  • La bandeja de salida (outbox) hace que la acción del usuario nunca dependa de la red; lanzar una excepción pide reintento; el UUID por cambio evita duplicados; y hay plan B para Safari, Firefox y permiso bloqueado.
  • Verificado: notificaciones, manejador de push (con mensaje inyectado), clic, sincronización, reintento disparado a mano, migración, y el servidor por separado (VAPID y cifrado). No verificado: la entrega real por el servicio de push, un teléfono real, iOS, el reintento automático del navegador y la batería.
