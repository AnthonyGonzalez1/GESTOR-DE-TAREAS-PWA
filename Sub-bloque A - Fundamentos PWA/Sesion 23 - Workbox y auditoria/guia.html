Workbox y auditoría

Dejamos de escribir cacheFirst()/networkFirst() a mano: Workbox encapsula ese trabajo en una librería real. Además, medimos qué tan bien soporta cada navegador lo que construimos, aplicamos patrones de UX propios de una PWA, y auditamos el resultado con la misma herramienta que usa la industria.

  • ✓Elegir entre GenerateSW e InjectManifest según si el proyecto necesita lógica propia dentro del Service Worker.
  • ✓Aplicar principios de UX/UI propios de una PWA: indicador de conexión, prompt de instalación personalizado, feedback de carga.
  • ✓Auditar una PWA real con Lighthouse, interpretar sus categorías, y aplicar al menos una mejora concreta a partir del resultado.

2Compatibilidad de navegadores

Las PWAs funcionan en cualquier dispositivo con un navegador moderno, ya que se basan en estándares web. Sin embargo, características avanzadas como la instalación y el soporte sin conexión dependen del navegador y del sistema operativo. En Latinoamérica, los navegadores más utilizados en los últimos años han sido Google Chrome (62.85% – 69.6%), Safari (15% – 20%) y Microsoft Edge (aproximadamente 5.5%). Aunque en general ofrecen un soporte sólido para las PWAs, Safari presenta algunas limitaciones importantes [1].

Chrome / Android62.85% – 69.6%Completobeforeinstallprompt automáticoReferencia de soporte completo

Cifras de cuota de navegador y limitaciones de Safari según Google, web.dev. Fuente: [1].

Consecuencia práctica: una PWA bien construida debe degradarse con gracia. Antes de usar cualquier API avanzada, se verifica su disponibilidad — nunca se asume soporte universal.

  navigator.serviceWorker.register('/sw.js');
}
if ('indexedDB' in window) {
  abrirBaseDeDatos();
}
if (window.crypto && crypto.subtle) {
  // cifrado disponible
}

3Workbox: qué es y sus módulos

Workbox es un conjunto de bibliotecas de código abierto que simplifica la gestión de service workers y el almacenamiento en caché en PWAs. Proporciona una interfaz más accesible para los desarrolladores al encapsular APIs de bajo nivel, como Service Worker y Cache Storage, facilitando su implementación. Es una herramienta ampliamente utilizada, presente en el 54% de los sitios móviles con service workers, y es compatible con frameworks y herramientas de compilación como Angular CLI, Create-React-App y Vue CLI [2].

workbox-routing

Gestiona las solicitudes interceptadas por el service worker, enrutándolas a funciones que generan respuestas adecuadas — el equivalente a los if/else por path que escribimos a mano en la Sesión 21.

workbox-strategies

Provee las estrategias de caché como clases ya implementadas: CacheFirst, NetworkFirst, StaleWhileRevalidate — las mismas estrategias de las Sesiones 20-21, sin escribirlas a mano.

workbox-precaching

Calcula un hash del contenido de cada archivo declarado y genera la lista de precaché automáticamente — es, literalmente, la respuesta a la limitación que vimos en la Sesión 29/32 con el Atlas 3D: la lista de precaché se genera, no se escribe a mano.

workbox-expiration

Administra la expiración de la caché, eliminando entradas según su antigüedad (maxAgeSeconds) o un límite máximo de elementos (maxEntries) — algo que nuestro cacheFirst() manual de la Sesión 20 nunca hizo: una vez que algo entraba al caché, se quedaba ahí para siempre.

workbox-window

Facilita la comunicación entre el service worker y la ventana del navegador, simplificando su registro y actualización [2].

El mismo enrutamiento por path que construimos a mano en la Sesión 21 se ve así, escrito directamente con los módulos de Workbox:

sw.js (con Workbox, escrito a mano)
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

registerRoute(
  ({ url }) => url.pathname.startsWith('/icons/'),
  new CacheFirst({
    cacheName: 'imagenes',
    plugins: [new ExpirationPlugin({ maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 })]
  })
);

registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new NetworkFirst({ cacheName: 'api-tareas' })
);

registerRoute(
  ({ request }) => ['document', 'script', 'style'].includes(request.destination),
  new StaleWhileRevalidate({ cacheName: 'shell' })
);

Es exactamente el mismo diseño que ya conocemos — tres rutas, tres estrategias — pero sin escribir cacheFirst(), networkFirst() ni staleWhileRevalidate() a mano, ni preocuparse por clonar respuestas o abrir el caché manualmente. Esto se escribe a mano importando los módulos — en la sección 4 vemos la otra forma, donde ni siquiera esto se escribe.

4GenerateSW vs. InjectManifest

Workbox ofrece dos formas de producir el Service Worker final. GenerateSW genera automáticamente un Service Worker completo a partir de un archivo de configuración: ni siquiera se escribe el código de la sección 3, solo se declara qué cachear y con qué estrategia. InjectManifest es la alternativa cuando el proyecto necesita lógica propia dentro del Service Worker (por ejemplo, manejar notificaciones push o sincronización en segundo plano) — Workbox solo se encarga de inyectar la lista de precaché dentro del archivo que el desarrollador escribe [3].

Demo real: generamos el sw.js del Gestor de Tareas

El Gestor de Tareas no usa un bundler — es HTML/CSS/JS plano, igual que en las Sesiones 15-22. Eso no impide usar Workbox: la CLI de Workbox calcula el hash de cada archivo real del proyecto directamente desde su contenido, sin necesitar un paso de build. Así se ve la configuración, apuntando a los archivos reales del checkpoint de la Sesión 22:

workbox-config.js
module.exports = {
  globDirectory: '.',
  globPatterns: ['index.html', 'manifest.json', 'css/*.css', '*.js', 'icons/*.png'],
  globIgnores: ['node_modules/**/*', 'workbox-config.js', 'package*.json'],
  swDest: 'sw.js',
  runtimeCaching: [
    {
      urlPattern: /\/icons\//,
      handler: 'CacheFirst',
      options: { cacheName: 'imagenes', expiration: { maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 } },
    },
    { urlPattern: /\/api\//, handler: 'NetworkFirst', options: { cacheName: 'api-tareas' } },
  ],
};
$ npx workbox-cli generateSW workbox-config.js

The service worker files were written to:
  • sw.js
  • sw.js.map
  • workbox-0cf22cab.js
The service worker will precache 10 URLs, totaling 25.9 kB.

Esto no es un número inventado — es la salida real de correr este comando contra el checkpoint de la Sesión 22. Workbox leyó cada archivo declarado en globPatterns, calculó un hash de su contenido, y escribió la lista de precaché con esos hashes como revision — la misma idea que resuelve la limitación de Vite en el Atlas 3D (Sesión 34), pero aplicada aquí a un proyecto sin bundler:

Tabla reducida a 8 de los 10 archivos precacheados, por espacio. Hashes truncados a 8 caracteres — en el sw.js generado aparecen completos.

No se edita a mano: sw.js queda minificado y con un hash distinto cada vez que cambia cualquier archivo precacheado — exactamente como el dist/ de un bundler. Se regenera con el mismo comando después de cada cambio, y se versiona en git como cualquier otro archivo generado (como un package-lock.json), nunca se edita directamente.

¿Cuándo preferir InjectManifest aquí? Hoy, GenerateSW alcanza porque el Gestor de Tareas no necesita lógica propia dentro del Service Worker. Eso cambia en la Sesión 26, cuando lleguen las notificaciones push: recibir un push y decidir qué notificación mostrar es lógica que Workbox no puede generar por configuración — ahí InjectManifest (precaché generado + self.addEventListener('push', ...) escrito a mano) será la opción correcta.

5UX/UI en PWAs

La Experiencia de Usuario (UX) y el Diseño de Interfaz de Usuario (UI) son conceptos clave en el desarrollo de software. La UX abarca la interacción general del usuario con la aplicación, incluyendo usabilidad, eficiencia y satisfacción. El UI es la interfaz visual que conecta al usuario con el sistema: un diseño efectivo no solo debe ser atractivo, sino también funcional, asegurando claridad, organización y consistencia [4].

Tres patrones de UX específicos de una PWA, que no aparecen en un sitio web tradicional:

  • Indicador de conexión: el usuario debe saber si está viendo datos frescos o una versión guardada en caché — un banner simple ("Sin conexión — mostrando datos guardados") evita confusión.
  • Prompt de instalación personalizado: Chrome/Edge disparan beforeinstallprompt, pero mostrarlo con un botón propio da control sobre el momento y el diseño.
  • Feedback de carga: como el Service Worker puede responder al instante desde caché o tardar por red, un skeleton screen evita que la app se sienta "congelada" en la primera carga.
app.js (prompt de instalación)
let deferredPrompt;
window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault();
  deferredPrompt = e;
  btnInstalar.hidden = false;
});
btnInstalar.addEventListener('click', async () => {
  deferredPrompt.prompt();
  const { outcome } = await deferredPrompt.userChoice;
  deferredPrompt = null;
});

Nota de compatibilidad: en Safari/iOS este evento nunca se dispara — ahí, la única opción es instruir al usuario con un mensaje visible ("Toca Compartir → Añadir a inicio").

6Auditando con Lighthouse

Lighthouse es la herramienta de auditoría automatizada de Google, integrada en Chrome DevTools, y también disponible como comando de terminal (npx lighthouse) o en PageSpeed Insights. Analiza una página cargada y genera un reporte con puntajes de 0 a 100 en varias categorías, además de una lista concreta de qué corregir en cada una [5].

CategoríaQué mide
PerformanceTiempos de carga y renderizado: First Contentful Paint, Largest Contentful Paint, bloqueo del hilo principal.
AccessibilityContraste de color, etiquetas ARIA, texto alternativo en imágenes, navegación por teclado.
Best PracticesUso de HTTPS, ausencia de librerías con vulnerabilidades conocidas, imágenes con proporciones correctas.
SEOMeta etiquetas, texto rastreable, enlaces con texto descriptivo.
Lo específico de una PWA no vive en una categoría aparte, sino en un conjunto de auditorías de instalabilidad dentro de Best Practices: manifest válido y enlazado, Service Worker registrado, HTTPS activo, y al menos un ícono de 512×512 — exactamente los requisitos que construimos en las Sesiones 16 y 17.

Cómo ejecutarlo: en Chrome, DevTools → pestaña Lighthouse → elegir categorías → Analyze page load. Desde la terminal, npx lighthouse https://mi-app.com --view genera el mismo reporte como archivo HTML.

7Caso real: el Gestor de tareas con Workbox y Lighthouse

Hasta hoy, el Gestor de Tareas reúne, en un solo proyecto, cada pieza vista desde la Sesión 15:

  • manifest.json completo, con íconos, colores y modo de visualización (Sesión 16).
  • sw.js, ahora generado por Workbox en lugar de escrito a mano, con las mismas tres estrategias por ruta y expiración real de íconos.
  • Datos de tareas persistidos en IndexedDB, con la nota privada cifrada con PBKDF2 + AES-GCM (Sesión 22).
  • Un botón de instalación propio, y un indicador de conexión visible en todo momento (UX/UI de esta sesión).
  • Un reporte de Lighthouse con las auditorías de instalabilidad en verde.

Todavía faltan las APIs de dispositivo y las notificaciones push (Sesiones 24-26) para que el Sub-bloque A quede realmente cerrado — hoy el proyecto queda automatizado y auditado, no terminado. El Sub-bloque B aplica exactamente esta misma migración a Workbox sobre el Atlas 3D en la Sesión 34, con una diferencia importante: ahí sí hay un bundler (Vite) de por medio, y esa diferencia es justo lo que resuelve la limitación de offline pendiente desde la Sesión 29.

Resumen de la sesión

  • La compatibilidad real de una PWA depende del navegador: Chrome y Edge ofrecen soporte completo, Safari/iOS tiene limitaciones importantes en instalación y actualización.
  • Workbox encapsula en módulos (routing, strategies, precaching, expiration, window) el mismo trabajo que se escribió a mano en las Sesiones 17-21 — y workbox-precaching calcula hashes de contenido automáticamente, generando la lista de precaché en vez de escribirla a mano.
  • GenerateSW automatiza todo el sw.js a partir de configuración — lo corrimos de verdad contra el Gestor de Tareas y precacheó 10 archivos, 25.9 kB. InjectManifest da control total cuando hace falta lógica propia (push, sync), como pasará en la Sesión 26.
  • Una buena UX de PWA avisa cuándo se está offline, ofrece un prompt de instalación propio, y da feedback de carga.
  • Lighthouse audita Performance, Accessibility, Best Practices y SEO, incluyendo el checklist de instalabilidad de una PWA — y una auditoría real sirve para encontrar mejoras concretas, no solo para obtener un puntaje.
  • El Gestor de Tareas automatiza su Service Worker y queda auditado hoy, pero el Sub-bloque A no cierra todavía: faltan las APIs de dispositivo y las notificaciones push (Sesiones 24-26).
