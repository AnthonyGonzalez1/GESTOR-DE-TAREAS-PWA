Almacenamiento y caché

Cómo el Service Worker guarda y recupera recursos con la interfaz Cache Storage — y en qué se diferencia del caché HTTP tradicional que el navegador ya maneja por su cuenta.

Objetivos de aprendizaje

  • ✓Distinguir el caché HTTP tradicional de la Cache Storage API: quién los controla y cómo.
  • ✓Usar las operaciones principales de la interfaz Cache: open, put, add/addAll, match, delete, keys.
  • ✓Explicar por qué la Cache Storage API existe de forma independiente al caché HTTP, y qué gana un Service Worker con eso.
  • ✓Versionar el nombre de un caché y limpiar versiones antiguas en el evento activate.
  • ✓Verificar en DevTools el contenido exacto de un Cache Storage del Gestor de tareas.

1Bienvenida y recap

En la Sesión 17 registramos el Service Worker del Gestor de tareas y cacheamos los recursos esenciales en el evento install con cache.addAll(). En la Sesión 18 aprendimos a leer ese caché de verdad, con caches.match() dentro de fetch. Las dos veces tratamos la interfaz Cache como una caja negra. Hoy la abrimos por completo: qué es exactamente un "caché" en el contexto de una PWA, cómo escribir en él a mano, y por qué es distinto del caché que el navegador ya maneja desde siempre.

2Dos mecanismos de caché

Cuando se habla de "caché" en el navegador, en realidad se habla de dos sistemas completamente independientes:

La interfaz Cache en los service workers es un mecanismo de almacenamiento independiente de la caché HTTP. Fuente: adaptado de [1].

Dato clave: la interfaz Cache ofrece un control más flexible a través de una API de JavaScript, permitiendo definir estrategias personalizadas sin que las configuraciones de la caché HTTP afecten directamente los recursos almacenados [1].

3El caché HTTP tradicional

El caché HTTP existe desde mucho antes que las PWA: es el mecanismo por el cual el navegador decide, sin preguntarle nada a JavaScript, si puede reutilizar una respuesta que ya descargó. Lo controla el servidor con encabezados en la respuesta:

  • Cache-Control: el encabezado principal — por ejemplo max-age=3600 (reutilizar por una hora) o no-store (nunca guardar).
  • ETag: una "huella digital" del recurso; el navegador la envía de vuelta para preguntar "¿cambió esto?" sin descargar el archivo completo.
  • Last-Modified: similar a ETag, pero basado en la fecha de la última modificación del recurso.

Este mecanismo funciona igual con o sin Service Worker — es responsabilidad del navegador y del servidor, no de la aplicación.

4La interfaz Cache: operaciones principales

La Cache Storage API expone dos objetos globales: caches (para administrar los cachés con nombre) y, dentro de cada uno, un objeto Cache (para administrar sus entradas). Estas son las operaciones que más se usan:

caches.open(nombre)

Abre (o crea) un caché con ese nombre y devuelve una promesa con el objeto Cache correspondiente.

cache.addAll([...])

Hace fetch() de cada URL de la lista y guarda automáticamente cada respuesta. La usamos en la Sesión 17.

cache.put(request, response)

Guarda una respuesta específica para una petición — control total, sin hacer fetch() por dentro.

cache.match(request)

Busca, dentro del caché, una respuesta guardada que coincida con la petición dada.

cache.delete(request)

Elimina una entrada específica del caché.

cache.keys()

Devuelve la lista de todas las peticiones (requests) guardadas en ese caché.

caches.keys()

Devuelve los nombres de todos los cachés que existen para el origen actual.

caches.delete(nombre)

Elimina un caché completo, con todas sus entradas.

5Cache Storage en la práctica

Con put() y match() se puede construir, a mano, el mismo comportamiento que addAll() hace automáticamente — pero con control total sobre cada paso:

sw.js (fragmento)
async function guardarManual() {
  const cache = await caches.open('gestor-tareas-v1');
  const respuesta = await fetch('/css/estilos.css');
  await cache.put('/css/estilos.css', respuesta);
}

async function buscarEnCache(peticion) {
  const cache = await caches.open('gestor-tareas-v1');
  const encontrado = await cache.match(peticion);
  return encontrado; // Response, o undefined si no está
}

Esta pareja — put() para guardar, match() para recuperar — es, en esencia, la base sobre la que se construyen las 5 estrategias de caché de la Sesión 20.

6Gestión de versiones y limpieza

Cada vez que se actualiza el contenido cacheado, conviene cambiar el nombre del caché (por ejemplo, de v1 a v2). Eso deja el caché viejo huérfano — y hay que borrarlo a mano en el evento activate, o se acumula espacio en el dispositivo del usuario para siempre:

sw.js (fragmento)
const CACHE_ACTUAL = 'gestor-tareas-v2';

self.addEventListener('activate', event => {
  event.waitUntil(
    caches.keys().then(nombres =>
      Promise.all(
        nombres
          .filter(nombre => nombre !== CACHE_ACTUAL)
          .map(nombre => caches.delete(nombre))
      )
    )
  );
});

El patrón es siempre el mismo: listar todos los cachés existentes con caches.keys(), filtrar los que no coinciden con la versión actual, y eliminarlos con caches.delete().

7Caso real: el sw.js actualizado

Juntando la limpieza de versiones con lo que ya teníamos de la Sesión 17, así queda el sw.js del Gestor de tareas:

sw.js
const CACHE_ACTUAL = 'gestor-tareas-v2';
const CORE_ASSETS = ['/index.html', '/css/estilos.css', '/js/app.js', '/manifest.json'];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_ACTUAL).then(cache => cache.addAll(CORE_ASSETS))
  );
});

self.addEventListener('activate', event => {
  event.waitUntil(
    caches.keys().then(nombres =>
      Promise.all(nombres.filter(n => n !== CACHE_ACTUAL).map(n => caches.delete(n)))
    ).then(() => self.clients.claim())
  );
});

self.addEventListener('fetch', event => {
  event.respondWith(fetch(event.request));
});

Para verificarlo: F12 → pestaña Application → sección Cache Storage. Ahí aparece gestor-tareas-v2 con cada uno de los recursos guardados, y se puede inspeccionar el contenido exacto de cada respuesta.

Resumen de la sesión

  • El caché HTTP lo controla el servidor con encabezados (Cache-Control, ETag) y funciona con o sin Service Worker.
  • La Cache Storage API es un mecanismo independiente, controlado por JavaScript, que requiere un Service Worker activo.
  • Operaciones clave: caches.open(), cache.put()/addAll(), cache.match(), cache.delete(), cache.keys(), caches.keys(), caches.delete().
  • put() + match() son la base de las estrategias de caché que vemos en la Sesión 20.
  • Versionar el nombre del caché y limpiar versiones antiguas en activate evita acumular espacio innecesario.
