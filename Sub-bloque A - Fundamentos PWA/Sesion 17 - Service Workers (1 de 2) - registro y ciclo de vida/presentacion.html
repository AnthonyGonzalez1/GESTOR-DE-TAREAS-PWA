SECCIÓN 01

¿Qué es un Service Worker?

Un script que el navegador ejecuta por separado de la página, en función de eventos.

Definición3 requisitos
¿Qué es un Service Worker? · 1.1

Un proxy programable entre la app y la red

Un bloque de código que la app instala en el navegador, y que se ejecuta según eventos — no según la interacción directa del usuario. Para instalarlo, el navegador exige tres requisitos:

Soporte

El navegador debe soportar la API de Service Workers.

HTTPS

O localhost durante el desarrollo.

Mismo origen

El script debe venir del mismo servidor que la app.

SECCIÓN 02

Registrar el Service Worker

Una llamada desde la página arranca todo el ciclo de vida.

navigator.serviceWorker.register()
Registro · 2.1

Una llamada en app.js

app.js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker
    .register('/sw.js')
    .then(reg => console.log('SW registrado:', reg.scope))
    .catch(err => console.error('Error al registrar SW:', err));
}
La comprobación if ('serviceWorker' in navigator) evita errores en navegadores muy antiguos.
SECCIÓN 03

El ciclo de vida completo

Seis fases, diseñadas para el funcionamiento offline y las actualizaciones eficientes.

6 fases
Ciclo de vida · 3.1

Las seis fases

1
"install"Registro e instalación

Se registra, y almacena en caché los recursos esenciales. Si falla, no se activa.

2
waitingEspera

Inactivo hasta que el SW anterior deje de controlar las sesiones activas.

3
"active"Activación

Asume el control, gestiona cachés y migra datos si hace falta.

4
"fetch"Interceptación

Hoy solo lo registramos y dejamos pasar la petición — interceptar de verdad es la Sesión 18.

5
"updatefound"Actualización

Activo hasta que se registra una nueva versión, instalada y puesta en espera.

6
skipWaiting()Salto de espera

Un SW nuevo puede activarse de inmediato en vez de esperar.

SECCIÓN 04

Limitaciones de los Service Workers

Muy poderosos, pero con límites concretos que conviene conocer desde ya.

Limitaciones

Cinco límites que conviene conocer

  • Solo se ejecutan si el navegador está abierto (algunos dispositivos mitigan esto en segundo plano).
  • No pueden manipular el DOM directamente — se comunican con la página por mensajes.
  • Su implementación puede resultar compleja pese al control detallado que ofrecen.
  • Las PWA no están en App Store ni Google Play — se instalan desde el navegador.
  • En iOS, las actualizaciones no son tan fluidas como en Android.
SECCIÓN 05

Caso real: el sw.js del Gestor de tareas

Registro, instalación y activación, juntos en un solo archivo — y cómo verificarlo.

sw.js completo
Caso real · 5.1

El sw.js completo

sw.js
const CACHE_NAME = 'gestor-tareas-v1';
const CORE_ASSETS = ['/index.html', '/css/estilos.css', '/js/app.js', '/manifest.json'];

self.addEventListener('install', event => {
  event.waitUntil(caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS)));
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(fetch(event.request));
});
El manejador de fetch está aquí porque el navegador lo exige para la instalabilidad — hoy solo deja pasar la petición. Interceptar de verdad llega en la Sesión 18.
Caso real · 5.2

Verificar en DevTools

DevTools

Resumen de la lección

  • Un Service Worker es un script separado de la página, sujeto a 3 requisitos: soporte, HTTPS, mismo origen.
  • Se registra con navigator.serviceWorker.register().
  • Su ciclo de vida tiene 6 fases: instalación, espera, activación, fetch, actualización, skipWaiting.
  • El fetch de hoy solo deja pasar la petición — interceptar de verdad y cachear rutas es la Sesión 18.
  • Con esto, el Gestor de tareas cumple, por primera vez, los 5 criterios de instalabilidad.
