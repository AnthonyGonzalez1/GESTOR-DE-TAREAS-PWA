El script que el navegador ejecuta por separado de la página: sus requisitos, cómo se registra, su ciclo de vida completo — registro, instalación, espera, activación, fetch y actualización — y sus limitaciones. Interceptar peticiones de verdad y cachear rutas llega en la Sesión 18.

Dato clave: al terminar la sesión de hoy, la pestaña "Installability" de DevTools debería mostrar los 5 criterios en verde por primera vez — el Gestor de tareas será, técnicamente, instalable.

2¿Qué es un Service Worker?

Un Service Worker es un bloque de código que una aplicación web instala en el navegador bajo ciertas condiciones, y que se ejecuta en función de eventos específicos — no de la interacción directa del usuario con la página. Permite añadir funcionalidades avanzadas, similares a las de una aplicación móvil, como el funcionamiento offline [1].

Para que el navegador acepte instalar un Service Worker, exige tres requisitos [1]:

  • Soporte del navegador: el navegador debe soportar la API de Service Workers (todos los navegadores modernos la soportan).
  • Conexión segura: la aplicación debe cargarse por HTTPS, o desde localhost durante el desarrollo.
  • Mismo origen: el script del Service Worker debe obtenerse desde el mismo servidor que la aplicación web — no se puede registrar un Service Worker de otro dominio.
Dato clave: el Service Worker se ejecuta en un hilo separado de la página, sin acceso directo al DOM. Es, en esencia, un proxy programable entre la aplicación y la red.

3Registrar el Service Worker

Todo empieza con una llamada desde el JavaScript de la página — normalmente en index.html o en el script principal — que le pide al navegador que registre el archivo del Service Worker:

app.js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker
    .register('/sw.js')
    .then(reg => console.log('SW registrado:', reg.scope))
    .catch(err => console.error('Error al registrar SW:', err));
}

La comprobación if ('serviceWorker' in navigator) es una buena práctica: evita errores en navegadores muy antiguos que no soportan la API. A partir de esta llamada, el navegador toma el control y arranca el ciclo de vida completo.

4El ciclo de vida completo

El ciclo de vida de un Service Worker está diseñado para mejorar la experiencia del usuario, permitiendo el funcionamiento offline, actualizaciones eficientes y el control de las solicitudes de red [2]. Tiene seis fases:

1
"install" eventRegistro e instalación

navigator.serviceWorker.register() registra el archivo. Durante el evento install, el Service Worker almacena en caché los recursos esenciales para funcionar offline. Si falla, no se activa.

2
waitingEspera

Permanece inactivo hasta que el Service Worker anterior deja de controlar las sesiones activas. Asegura que nunca haya más de un Service Worker activo al mismo tiempo.

3
"active" eventActivación

Una vez activado, el Service Worker asume el control de la aplicación, gestionando cachés y migrando datos si es necesario.

4
"fetch" eventInterceptación de solicitudes

Se dispara con cada petición de red de la aplicación. Hoy solo lo registramos y lo dejamos pasar tal cual a la red — interceptar de verdad y responder desde la caché es el tema completo de la Sesión 18.

5
"updatefound" eventActualización

El Service Worker se mantiene activo hasta que se registra una nueva versión. El navegador la instala y la deja en espera hasta reemplazar a la anterior [3].

6
skipWaiting()Salto de espera (opcional)

Un Service Worker nuevo puede llamar a skipWaiting() para activarse de inmediato en vez de esperar a que se cierren todas las pestañas abiertas.

Las seis fases del ciclo de vida de un Service Worker. Fuente: adaptado de J. Wargo, "Fig. 3: Ciclo de vida de un service worker" [2][3].

5Limitaciones de los Service Workers

Aunque son muy poderosos, los Service Workers tienen límites concretos que conviene conocer desde ya [4]:

  • Solo se ejecutan si el navegador está abierto. En algunos dispositivos el navegador puede seguir corriendo en segundo plano, lo que mitiga parcialmente esta limitación.
  • No pueden manipular el DOM de la aplicación directamente — existen métodos de comunicación alternativos (mensajes) entre la página y el Service Worker.
  • Su implementación puede resultar compleja, a pesar de ofrecer un control muy detallado sobre caché y solicitudes de red.
  • Las PWA no están disponibles en tiendas como App Store o Google Play — deben instalarse directamente desde el navegador, lo que puede dificultar su adopción por algunos usuarios.
  • En iOS, las actualizaciones automáticas no son tan fluidas como en Android: el usuario suele tener que abrir la PWA manualmente para que se actualice el contenido.

6Caso real: el sw.js del Gestor de tareas

Juntando el registro, la instalación y la activación, este es el sw.js mínimo que agregamos hoy al proyecto. El manejador de fetch está presente porque el navegador lo exige para considerar instalable la aplicación, pero por ahora solo deja pasar la petición a la red tal cual — interceptar de verdad y responder desde la caché llega en la Sesión 18:

sw.js
const CACHE_NAME = 'gestor-tareas-v1';
const CORE_ASSETS = [
  '/index.html',
  '/css/estilos.css',
  '/js/app.js',
  '/manifest.json',
];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(CORE_ASSETS))
  );
});

self.addEventListener('activate', event => {
  event.waitUntil(self.clients.claim());
});

self.addEventListener('fetch', event => {
  event.respondWith(fetch(event.request));
});

Para verificarlo: F12 → pestaña Application → sección Service Workers. Chrome debe mostrar el script registrado, con estado activated and is running. Y en la sección Manifest, la lista de "Installability" debería mostrar, por fin, los 5 criterios en verde.

Resumen de la sesión

  • Un Service Worker es un script que el navegador ejecuta por separado de la página, bajo tres requisitos: soporte del navegador, HTTPS (o localhost), y mismo origen.
  • Se registra con navigator.serviceWorker.register().
  • Su ciclo de vida tiene seis fases: registro/instalación, espera, activación, fetch, actualización, y el salto opcional con skipWaiting().
  • El evento fetch de hoy es un simple registro que deja pasar la petición a la red — interceptar de verdad y cachear rutas es el tema completo de la Sesión 18.
  • Tiene límites reales: solo corre con el navegador abierto, no toca el DOM directamente, y no vive en tiendas de aplicaciones.
  • Con el Service Worker de hoy, el Gestor de tareas cumple, por primera vez, los 5 criterios de instalabilidad.
