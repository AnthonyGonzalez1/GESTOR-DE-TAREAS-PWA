IndexedDB y Web Crypto API

Cuando un simple par clave-valor en el caché no alcanza: cómo guardar datos estructurados y consultables en el navegador, versionar el esquema con el tiempo, y cifrar los campos sensibles con una clave derivada de una contraseña real — no una clave de juguete que se pierde al recargar la página.

Objetivos de aprendizaje

  • ✓Explicar por qué un caché de pares clave-valor no alcanza para datos estructurados, consultables y que crecen con el tiempo.
  • ✓Crear y versionar una base de datos IndexedDB con object stores, índices, y una migración real entre versiones del esquema.
  • ✓Realizar operaciones CRUD completas (add, put, get, delete, getAll, count) y recorrer/editar resultados con un cursor.
  • ✓Derivar una clave criptográfica real a partir de una contraseña del usuario con PBKDF2 — no una clave aleatoria que se pierde al recargar.
  • ✓Cifrar, descifrar y verificar integridad de datos sensibles con AES-GCM y SHA-256 antes de guardarlos en IndexedDB.
  • ✓Reconocer qué protege realmente el cifrado en el cliente, y qué no.

Recursos de esta sesión

  • Descargar .zipCheckpoint — cierre de la Sesión 21. El Gestor de Tareas con las 5 estrategias de caché ya enrutadas por tipo de recurso. Hoy no tocamos el caché — agregamos almacenamiento estructurado aparte, con IndexedDB.

1Bienvenida y recap

En la Sesión 21 cerramos las 5 estrategias de caché y aprendimos a enrutarlas por tipo de recurso dentro de fetch. Pero tanto el caché HTTP como la Cache Storage API comparten una limitación de fondo: guardan pares Request → Response, es decir, archivos completos. Ninguno de los dos sabe responder preguntas como "dame todas las tareas con prioridad alta" sin descargar y revisar cada archivo uno por uno, y ninguno soporta actualizar un solo campo de un registro sin reescribir el archivo entero. Hoy resolvemos eso con IndexedDB — y de paso aprendemos a cifrar los datos más sensibles que guardamos ahí, con una clave que de verdad sobrevive entre sesiones del usuario.

2De Cache Storage a IndexedDB

El funcionamiento sin conexión en una PWA se logra combinando tecnologías distintas para trabajos distintos. La Cache Storage API permite a los service workers almacenar en caché respuestas a solicitudes de red, asegurando que recursos esenciales como HTML, CSS, JavaScript e imágenes puedan cargarse sin depender de la conexión. IndexedDB, en cambio, proporciona almacenamiento estructurado para datos dinámicos, permitiendo consultas por campo y sincronización con el servidor cuando la conexión se restablece [1].

3Abrir y versionar una base de datos

IndexedDB es asíncrona pero basada en eventos, no en promesas — a diferencia de fetch() o de la Web Crypto API que veremos más adelante. Abrir una base de datos dispara hasta tres eventos posibles:

  • onupgradeneeded: se dispara solo cuando la base de datos no existe, o cuando el número de versión aumenta. Aquí — y solo aquí — se pueden crear, modificar o borrar object stores e índices.
  • onsuccess: la base de datos quedó abierta y lista para usarse.
  • onerror: algo falló — por ejemplo, el usuario negó el permiso de almacenamiento, o quedó sin espacio.
db.js
function abrirBaseDeDatos() {
  return new Promise((resolve, reject) => {
    const peticion = indexedDB.open('gestor-tareas-db', 1);

    peticion.onupgradeneeded = event => {
      const db = event.target.result;
      const store = db.createObjectStore('tareas', { keyPath: 'id', autoIncrement: true });
      store.createIndex('porPrioridad', 'prioridad', { unique: false });
      store.createIndex('porTitulo', 'titulo', { unique: true });
    };

    peticion.onsuccess = event => resolve(event.target.result);
    peticion.onerror = event => reject(event.target.error);
  });
}

createObjectStore() es el equivalente a crear una tabla; keyPath indica qué propiedad del objeto sirve como clave única (aquí, id), y autoIncrement hace que IndexedDB genere ese id automáticamente. createIndex() crea un índice secundario — aquí, uno para buscar tareas por prioridad sin recorrerlas todas, y otro que exige título único con { unique: true }.

Migrar el esquema: qué pasa cuando la versión sube

Un proyecto real no diseña su esquema una sola vez. Cuando el Gestor de tareas necesite, por ejemplo, agrupar tareas por proyecto, hay que subir el número de versión y onupgradeneeded se dispara de nuevo — pero esta vez con datos ya guardados por los usuarios que hay que preservar:

db.js (migración v1 → v2)
const peticion = indexedDB.open('gestor-tareas-db', 2);  // subimos de 1 a 2

peticion.onupgradeneeded = event => {
  const db = event.target.result;
  const tx = event.target.transaction;
  const version = event.oldVersion;  // versión desde la que se migra

  if (version < 1) {
    const store = db.createObjectStore('tareas', { keyPath: 'id', autoIncrement: true });
    store.createIndex('porPrioridad', 'prioridad', { unique: false });
  }
  if (version < 2) {
    // Nuevo en la v2: índice por proyecto, sobre el store que ya existía
    const store = tx.objectStore('tareas');
    store.createIndex('porProyecto', 'proyectoId', { unique: false });
  }
};

event.oldVersion dice desde qué versión viene el navegador de ese usuario — puede ser 0 (base de datos nueva) o cualquier versión anterior. El patrón if (version < N) encadenado deja que un usuario que nunca abrió la app salte directo a la v2, y uno que ya tenía la v1 solo reciba el índice nuevo, sin perder sus tareas guardadas. Intentar crear un object store o índice que ya existe lanza un error — de ahí que cada bloque solo corra si hace falta.

4Operaciones CRUD con IndexedDB

Toda operación de lectura o escritura ocurre dentro de una transacción, que declara de antemano qué object stores va a tocar y en qué modo. Una transacción se cierra sola (oncomplete) cuando todas sus operaciones terminan, o se cancela entera (onabort) si una falla — no hay una mezcla parcial de cambios.

db.transaction(stores, modo)

Abre una transacción. modo es 'readonly' o 'readwrite'.

tx.objectStore(nombre)

Obtiene el object store dentro de esa transacción.

store.add(objeto)

Inserta un registro nuevo. Falla si la clave ya existe.

store.put(objeto)

Inserta o actualiza — sin fallar si la clave ya existe.

store.get(clave)

Recupera un único registro por su clave.

store.delete(clave)

Elimina un registro por su clave.

store.getAll()

Recupera todos los registros del store.

store.count()

Cuenta cuántos registros hay, sin traerlos.

Ojo: estas operaciones NO devuelven promesas — devuelven un objeto IDBRequest con sus propios onsuccess/onerror. Es habitual (y muy recomendable) envolverlas en una Promise propia para poder usar async/await, como en el ejemplo siguiente. En un proyecto real es común además usar una librería ligera como idb (de Jake Archibald) que hace exactamente esto por ti — aquí lo escribimos a mano para entender qué hay detrás.
db.js
function agregarTarea(db, tarea) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction('tareas', 'readwrite');
    const peticion = tx.objectStore('tareas').add(tarea);
    peticion.onsuccess = () => resolve(peticion.result);
    peticion.onerror = () => reject(peticion.error);
    tx.onabort = () => reject(tx.error);
  });
}

function obtenerTarea(db, id) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction('tareas', 'readonly');
    const peticion = tx.objectStore('tareas').get(id);
    peticion.onsuccess = () => resolve(peticion.result);
    peticion.onerror = () => reject(peticion.error);
  });
}

// Uso, ahora con await:
const id = await agregarTarea(db, { titulo: 'Estudiar IndexedDB', prioridad: 'alta', hecha: false });
const tarea = await obtenerTarea(db, id);

5Consultas con índices y cursores

getAll() trae todo el store — perfecto para pocos registros, ineficiente para muchos. Para consultas dirigidas se usan los índices creados con createIndex(), y para recorrer resultados uno a uno sin cargarlos todos en memoria —o para editarlos o borrarlos mientras se recorren— un cursor:

db.js
function tareasPorPrioridad(db, prioridad) {
  return new Promise((resolve) => {
    const resultado = [];
    const store = db.transaction('tareas', 'readonly').objectStore('tareas');
    const indice = store.index('porPrioridad');
    const cursor = indice.openCursor(IDBKeyRange.only(prioridad));

    cursor.onsuccess = event => {
      const c = event.target.result;
      if (c) {
        resultado.push(c.value);
        c.continue();  // avanza al siguiente registro que coincide
      } else {
        resolve(resultado);  // no hay más — terminamos
      }
    };
  });
}

// Marcar como hechas todas las tareas de prioridad "baja", con el cursor en modo escritura:
function completarTareasDeBajaPrioridad(db) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction('tareas', 'readwrite');
    const indice = tx.objectStore('tareas').index('porPrioridad');
    const cursor = indice.openCursor(IDBKeyRange.only('baja'));
    let actualizadas = 0;

    cursor.onsuccess = event => {
      const c = event.target.result;
      if (!c) return resolve(actualizadas);
      const registro = c.value;
      registro.hecha = true;
      c.update(registro);   // reescribe el registro actual sin cerrar el cursor
      actualizadas++;
      c.continue();
    };
    tx.onerror = () => reject(tx.error);
  });
}

IDBKeyRange.only(valor) limita el cursor a las entradas cuyo índice coincide exactamente; también existen IDBKeyRange.bound(), lowerBound() y upperBound() para rangos, y openCursor(range, 'prev') para recorrer en orden descendente. El patrón c.continue() dentro de onsuccess es lo que hace avanzar el cursor — olvidarlo deja el bucle detenido en el primer resultado. c.update(objeto) y c.delete() operan sobre el registro que el cursor tiene enfocado en ese momento, sin necesitar su clave por separado.

6Web Crypto API: fundamentos

La API Web Crypto permite realizar operaciones criptográficas en entornos seguros, proporcionando primitivas de bajo nivel para el cifrado de datos y para verificar su integridad. Su uso requiere un manejo cuidadoso para evitar vulnerabilidades. Solo funciona en conexiones HTTPS (o localhost) y es compatible con Web Workers, lo que permite realizar procesos criptográficos en segundo plano [3].

  • window.crypto.subtle: el objeto que expone todas las operaciones — generar y derivar claves, cifrar, descifrar, calcular hashes.
  • Basada en promesas: a diferencia de IndexedDB, cada método de crypto.subtle devuelve una Promise — se puede usar await directamente.
  • Solo HTTPS: igual que los Service Workers, crypto.subtle no está disponible en páginas servidas por HTTP simple (excepto localhost).

Además de cifrar, crypto.subtle calcula hashes — huellas digitales de un dato, útiles para verificar que no fue alterado sin necesitar guardar el dato original:

crypto.js
async function calcularHash(texto) {
  const datos = new TextEncoder().encode(texto);
  const buffer = await crypto.subtle.digest('SHA-256', datos);
  return Array.from(new Uint8Array(buffer))
    .map(b => b.toString(16).padStart(2, '0'))
    .join('');  // hash en hexadecimal, listo para comparar o guardar
}
Dato clave: AES-GCM es el algoritmo recomendado por MDN para cifrado simétrico de propósito general en el navegador — es rápido y además detecta si el texto cifrado fue alterado. SHA-256 es el algoritmo de hash recomendado cuando hace falta verificar integridad sin cifrar.

7Derivar una clave real: PBKDF2 desde una contraseña

Una clave generada con crypto.subtle.generateKey() es aleatoria — perfecta para una demo, inútil en la práctica: si no se guarda en ningún lado, se pierde en cuanto se recarga la página, y con ella, todo lo cifrado. Lo que un proyecto real necesita es una clave que el usuario pueda reproducir cada vez que abre la app, típicamente a partir de una contraseña que él mismo recuerda. Para eso existe PBKDF2 (Password-Based Key Derivation Function 2): toma una contraseña y una sal (salt) aleatoria, y las combina miles de veces para producir una clave — deliberadamente lento, para que probar contraseñas por fuerza bruta sea costoso.

crypto.js
async function derivarClaveDesdeContrasena(contrasena, sal) {
  // 1. La contraseña entra como material crudo, todavía no es una CryptoKey utilizable
  const materialBase = await crypto.subtle.importKey(
    'raw',
    new TextEncoder().encode(contrasena),
    'PBKDF2',
    false,
    ['deriveKey']
  );

  // 2. PBKDF2 combina la contraseña y la sal 100 000 veces para producir la clave real
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt: sal, iterations: 100000, hash: 'SHA-256' },
    materialBase,
    { name: 'AES-GCM', length: 256 },
    false,                    // no exportable: se re-deriva cada vez, no se guarda
    ['encrypt', 'decrypt']
  );
}

// La sal no es secreta, pero debe guardarse junto a los datos cifrados —
// sin ella, ni siquiera la contraseña correcta reproduce la misma clave.
const sal = crypto.getRandomValues(new Uint8Array(16));
const clave = await derivarClaveDesdeContrasena(contrasenaDelUsuario, sal);

Con este cambio, la clave ya no vive solo en memoria: se puede reconstruir en cualquier sesión futura con la misma contraseña y la misma sal — la sal se guarda en IndexedDB junto al dato cifrado (no es secreta), pero la contraseña nunca se guarda en ningún lado. Es exactamente el mismo principio que usa un gestor de contraseñas: la contraseña maestra nunca se envía ni se almacena, solo se usa, en el momento, para derivar la clave.

100 000 iteraciones no es un número mágico: es el mínimo que OWASP recomendaba para PBKDF2-SHA256 al momento de escribir esta guía — y sube con el tiempo, a medida que el hardware se vuelve más rápido para probar contraseñas. En un proyecto real conviene revisar la recomendación vigente en vez de copiar este número indefinidamente.

8Cifrar y descifrar con AES-GCM

Con la clave ya derivada, cifrar un texto requiere además un vector de inicialización (IV) aleatorio y distinto en cada operación, y los datos convertidos a bytes con TextEncoder:

crypto.js
async function cifrarTexto(clave, texto) {
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const datos = new TextEncoder().encode(texto);
  const cifrado = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, clave, datos);
  return { cifrado, iv };  // el IV se guarda junto al cifrado, no es secreto
}

async function descifrarTexto(clave, { cifrado, iv }) {
  const datos = await crypto.subtle.decrypt({ name: 'AES-GCM', iv }, clave, cifrado);
  return new TextDecoder().decode(datos);
}

El IV no es secreto — se puede guardar en texto plano junto al dato cifrado — pero debe ser distinto cada vez que se cifra algo con la misma clave, o AES-GCM pierde sus garantías de seguridad. crypto.getRandomValues() ya garantiza esa aleatoriedad. Si se intenta descifrar con la clave o el IV equivocados, o si el cifrado fue alterado, decrypt() rechaza la promesa en vez de devolver datos corruptos silenciosamente — así es como AES-GCM detecta manipulación.

Sobre guardar la clave: una CryptoKey no exportable como la de la sección 7 no se puede leer ni guardar directamente — solo se puede volver a derivar con la contraseña. Eso es intencional: cualquier persona con acceso al navegador del usuario (perfil local, extensión maliciosa) que sí encontrara una clave guardada podría descifrar todo sin conocer la contraseña. El cifrado en el cliente protege contra fugas de la base de datos del servidor o de terceros que interceptan el tráfico — no contra alguien con acceso físico al dispositivo ya desbloqueado y a la contraseña en uso.

9Caso real: el Gestor de tareas con datos cifrados

No todo necesita cifrarse — cifrar campos que se usan para buscar o filtrar los vuelve inconsultables sin descifrar cada registro primero. El patrón real: cifrar solo lo sensible, dejar el resto plano y consultable, y usar la clave derivada por contraseña de la sección 7 en vez de una clave de un solo uso:

db.js
async function guardarTareaConNota(db, clave, tarea) {
  const { cifrado, iv } = await cifrarTexto(clave, tarea.notaPrivada);
  const registro = {
    titulo: tarea.titulo,           // plano: se busca y se filtra
    prioridad: tarea.prioridad,     // plano: tiene un índice
    notaCifrada: cifrado,           // cifrado: solo se lee de a uno
    notaIv: iv,
  };
  return agregarTarea(db, registro);
}

async function leerNotaPrivada(clave, registro) {
  return descifrarTexto(clave, { cifrado: registro.notaCifrada, iv: registro.notaIv });
}

Con esto, el Gestor de tareas puede seguir filtrando por prioridad instantáneamente con el índice de la sección 5, mientras que la nota privada de cada tarea solo se descifra cuando el usuario abre esa tarea en particular — y solo si conoce la contraseña que reconstruye la clave. La sal (sección 7) se guarda una sola vez, aparte, en un registro de configuración del propio Gestor de tareas.

Para verificarlo: DevTools → Application → IndexedDB → gestor-tareas-db → tareas. El campo notaCifrada debe verse como un ArrayBuffer de bytes ilegibles, nunca como el texto original — si se ve el texto plano ahí, el cifrado no se está aplicando antes de guardar.

Resumen de la sesión

  • IndexedDB guarda objetos estructurados y consultables — a diferencia de Cache Storage (archivos) y localStorage (texto plano, síncrono).
  • Object stores e índices se crean o modifican solo dentro de onupgradeneeded; event.oldVersion permite migrar el esquema sin perder datos existentes.
  • IndexedDB es basada en eventos (onsuccess/onerror), no en promesas — conviene envolverla para usar async/await. Un cursor permite recorrer, actualizar (update()) o borrar (delete()) registros uno a uno sin cargarlos todos en memoria.
  • La Web Crypto API (basada en promesas, solo HTTPS) permite calcular hashes con SHA-256 y cifrar con AES-GCM.
  • PBKDF2 deriva una clave real y reproducible a partir de una contraseña del usuario y una sal — muy distinto de una clave aleatoria que se pierde al recargar.
  • El patrón real: cifrar solo los campos sensibles, dejando el resto plano y consultable con índices; el cifrado en el cliente protege contra fugas de servidor o de red, no contra acceso físico al dispositivo ya desbloqueado.
